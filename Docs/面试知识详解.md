# 第一部分 · C# 语言

## 1.1 值类型 vs 引用类型

**结论**：区别在于变量里装的是什么。值类型装数据本身，引用类型装数据的地址。

| | 值类型 | 引用类型 |
| --- | --- | --- |
| 常见类型 | `int` `float` `bool` `enum` `struct` `Vector2` `Color` | `class` `string` 数组 委托 接口 |
| 变量内容 | 数据本身 | 指向堆上对象的引用 |
| 赋值语义 | 复制一份数据 | 复制引用，两个变量指向同一对象 |
| 能否为 null | 一般不能（除非 `int?`） | 可以 |
| 能否继承 | 不能 | 能 |

```csharp
// 值类型：复制
Vector2 a = new Vector2(1f, 2f);
Vector2 b = a;
b.x = 99f;
Debug.Log(a.x);   // 1 —— a 完全不受影响

// 引用类型：共享
var listA = new List<int>();
var listB = listA;
listB.Add(1);
Debug.Log(listA.Count);   // 1 —— 是同一个对象
```

**常见误解：「值类型存在栈上」。** 准确说法是：值类型变量存在**它被声明的位置**。

| 声明位置 | 存在哪 |
| --- | --- |
| 方法内的局部变量、方法参数 | 栈 |
| 作为 class 的字段 | 跟着对象在堆上 |
| 作为数组的元素 | 在数组的堆内存里，连续排列 |
| 被装箱之后 | 堆 |

第三行很实用：`Vector2[]` 是一整块连续内存，缓存友好，比「`Vector2` 的 class 数组」快得多。

**什么时候该用 struct**：小（经验值 ≤ 16 字节）、生命周期短、不需要继承和多态、语义上「值」比「对象」更自然。

**你项目里的例子**

```csharp
public struct DamageInfo { ... }   // Scripts/Combat/DamageInfo.cs
public struct HitResult  { ... }   // Scripts/Combat/DamageResolver.cs
```

每次命中都要构造一次 `DamageInfo`。写成 struct 就完全不产生 GC；写成 class，每一次挥击都会在堆上留下一个待回收对象。动作游戏一秒命中十几次，这就是区别。

## 1.2 装箱与拆箱

**结论**：装箱 = 把值类型塞进 `object` 类型的变量，要在堆上分配一个盒子；拆箱 = 从盒子里取回值。**装箱产生 GC，是常见的隐性性能杀手。**

```csharp
int n = 42;
object box = n;        // 装箱：堆上分配，把 42 复制进去
int back = (int)box;   // 拆箱：把值复制出来
```

**什么时候会偷偷装箱**

```csharp
// 1. 非泛型集合
ArrayList list = new ArrayList();
list.Add(1);              // 装箱
foreach (int x in list)   // 每次迭代拆箱
    Debug.Log(x);

// 2. 值类型被当作接口使用
IComparable c = 5;        // 装箱（接口是引用类型）

// 3. 格式化
string.Format("{0}", 42); // 装箱
"值：" + 42;              // 不装箱（C# 有专门的 Concat(int) 重载）
```

**为什么 `List<T>` 不装箱而 `ArrayList` 装箱**：`List<T>` 内部是 `T[]`，元素就是值类型本身；`ArrayList` 内部是 `object[]`，任何东西进去都得变成 `object`。

顺带一个高频细节：**`List<T>` 的 `foreach` 不装箱**。

```csharp
foreach (var x in list)                     // 编译器直接内联 List<T>.Enumerator —— 零装箱
foreach (var x in (IEnumerable<int>)list)   // 走接口，枚举器被装箱
```

**你项目里的例子**：`UIManager._registered` 是 `Dictionary<Type, UIPanel>`，`Health.ApplyDamage` 全程用 `float` 传参，都不经过 `object`，没有装箱。

**一句话记住**：看到「值类型赋给 `object` 或接口变量」，就有装箱。

## 1.3 继承 / 抽象类 / 接口

**结论**：三者解决不同问题。继承表达「是一个」，抽象类表达「是一类东西、细节留给你填」，接口表达「具备某种能力」。

| | 抽象类 | 接口 |
| --- | --- | --- |
| 能否有字段 | 能 | 不能（C# 8 前） |
| 能否有实现 | 能 | C# 8 起可以，但实践中仍当契约用 |
| 多继承 | 只能继承一个 | 可以实现多个 |
| 语义 | 是一类东西 | 具备某种能力 |
| 典型用途 | 共享代码 + 强制实现 | 解耦调用方与被调用方 |

**什么时候用哪个**

- 多个类**共享一部分实现**，且确实是同一类东西 → 抽象类
- 只要求「必须提供某个方法」，且希望**与具体类型无关** → 接口

**你项目里的例子（很好的对比素材）**

```csharp
// 抽象类：所有面板共享「打开 / 关闭 / 是否打开」这套实现
public abstract class UIPanel : MonoBehaviour { ... }   // Scripts/UI/UIPanel.cs

// 接口：谁有能力防守？DamageResolver 只关心"能不能"，不关心"是谁"
public interface IDamageGuard  { BlockOutcome EvaluateBlock(ref DamageInfo info); ... }
public interface IInterruptible { void Interrupt(int frames, string reason); }
```

为什么 `IDamageGuard` 用接口而不是抽象基类？因为 `PlayerCombat` 已经继承了 `MonoBehaviour`——**C# 只允许单继承**。如果防守能力做成抽象类，`PlayerCombat` 就没法同时是「战斗控制器」和「防守者」。

面试时务必把这句话讲出来：**Unity 里 `MonoBehaviour` 占掉了唯一的继承名额，所以「能力」几乎一律用接口实现。**

## 1.4 virtual / override / new

**结论**：`virtual` 声明「可被改写」，`override` 改写它（多态生效），`new` 只是把父类成员**隐藏**起来（多态失效，是坑）。

```csharp
class Base     { public virtual void Speak() { Debug.Log("Base"); } }
class A : Base { public override void Speak() { Debug.Log("A"); } }   // 改写
class B : Base { public new void Speak()      { Debug.Log("B"); } }   // 隐藏

Base x = new A();
x.Speak();   // A    —— override 生效

Base y = new B();
y.Speak();   // Base —— 调的是父类的！new 在多态下失效

B z = new B();
z.Speak();   // B    —— 只有变量声明类型是 B 时才走新的
```

**为什么 `new` 是坑**：它不报错，行为却取决于「变量声明成什么类型」。这种「有时候对、有时候不对」的 bug 最难查——和你错题本里 `Vector2` 分量写反属于同一类毛病。

**补充**：`base.Speak()` 可以显式调父类实现；`sealed override` 可以终止后续改写；`abstract` 方法必须被 `override`，否则编译不过。

**你项目里的例子**：`UIPanel` 里的 `Init()` / `OnOpen()` 一类钩子应该用 `virtual` + `override`。如果误用 `new`，那么 `UIManager` 用 `UIPanel` 类型持有引用时就会调到空实现——**这是错题本 009「泛型类型对不上，静默什么都不做」的亲戚**。

## 1.5 委托与事件

**结论**：委托是「能装方法的变量」；事件是「加了访问限制的委托」——外部只能 `+=` / `-=`，不能直接调用或清空。

```csharp
// 委托：能赋值、能调用
public Action<int> OnHit;
OnHit = null;
OnHit?.Invoke(5);

// 事件：外部只能订阅
public event Action<float> Damaged;
// 外部: health.Damaged += Handler;   ✓
// 外部: health.Damaged();            ✗ 编译不过 —— 这正是 event 存在的意义
```

**多播**：一个委托可以挂多个方法，`+=` 追加，调用时按顺序全部执行。

```csharp
Health.Damaged += OnPlayerDamaged;   // UI 更新血条
Health.Damaged += OnShakeCamera;     // 震屏
```

**订阅与取消订阅必须成对**

```csharp
void Awake()     { if (Health != null) Health.Damaged += OnDamaged; }
void OnDestroy() { if (Health != null) Health.Damaged -= OnDamaged; }
```

这就是你 `PlayerCombat.cs` 里的真实写法。**为什么必须 `-=`**：

- 事件持有指向订阅者方法的引用。只要事件还活着，订阅者对象就**不会被 GC 回收**——Unity 里最经典的内存泄漏。
- 静态事件尤其危险：静态字段生命周期是整个进程，订阅了不取消，对象永久泄漏。
- 更隐蔽的一种：对象已经 `Destroy` 了，事件列表里还留着它的回调，一触发就抛 `MissingReferenceException`。

**注意**：`-=` 只移除**同一个方法引用**。匿名方法取消不掉：

```csharp
health.Damaged += (d) => Debug.Log(d);   // 拿不到这个委托的引用，永远取消不了
```

所以「必须能取消订阅」的场合，老实写具名方法。

## 1.6 Lambda 与闭包

**结论**：闭包 = Lambda 捕获了外部变量。被捕获的变量会被「提升」到编译器生成的类里，**生命周期被延长，并且产生堆分配**。

```csharp
int count = 0;
Action act = () => count++;   // count 被提升到堆上的对象里
act();
Debug.Log(count);             // 1 —— 外部变量真的被改了
```

**经典坑之一：循环变量捕获**

```csharp
// foreach —— C# 5 起每次迭代是全新的变量，行为符合直觉
foreach (var i in new[] { 1, 2, 3 })
    actions.Add(() => Debug.Log(i));   // 输出 1 2 3 ✓

// for —— 变量只有一个，被所有闭包共享
for (int i = 0; i < 3; i++)
    actions.Add(() => Debug.Log(i));   // 输出 3 3 3 ✗

// 修法：循环体内复制一份
for (int i = 0; i < 3; i++)
{
    int local = i;
    actions.Add(() => Debug.Log(local));   // 0 1 2 ✓
}
```

**经典坑之二：每帧新建 Lambda = 每帧分配**

```csharp
void Update()
{
    button.onClick.AddListener(() => DoSomething());   // 每帧加一个监听，还取消不掉
}
```

游戏中常见的 GC 抖动来源。`AddListener` 应该写在 `Awake` / `Start` 里一次。

**闭包还会捕获 `this`**：Lambda 体里访问了实例成员（`transform`、`Motor`、实例方法），编译器就会顺带捕获 `this`，多一个分配。

**面试加分回答**：「不想有闭包分配怎么办？」→ 把状态存成字段、改用具名方法，或用静态方法 + 显式参数传递。

## 1.7 泛型与约束

**结论**：泛型让「同一套代码适配不同类型」而不装箱、不丢类型信息；`where` 约束是给编译器提供保证，让泛型体里能用上这些保证。

| 约束 | 含义 | 能做什么 |
| --- | --- | --- |
| `where T : class` | 引用类型 | 可以判 `null` |
| `where T : struct` | 值类型 | 无装箱 |
| `where T : new()` | 有无参构造函数 | 可以 `new T()` |
| `where T : Component` | 必须是组件 | 可以 `AddComponent<T>()` |
| `where T : UIPanel` | 是 `UIPanel` 或其子类 | 能访问 `UIPanel` 的成员 |
| `where T : IInterruptible` | 具备该能力 | 能调接口方法 |

**约束在干什么**

```csharp
public T GetOrCreate<T>() where T : UIPanel
{
    var existing = Get<T>();
    if (existing != null) return existing;

    var go = new GameObject(typeof(T).Name);
    return go.AddComponent<T>();   // T 被约束为 UIPanel（本质是 Component），这行才编得过
}
```

你项目里这一个方法同时用到了：泛型、约束、`typeof(T).Name`（运行期取类型名）。

**同一个方法的反面案例（错题本 009）**

```csharp
UIManager.Instance.HidePanel<BasePanel>();  // ✗ 字典 key 是 "BagPanel"，查不到 → 静默返回
UIManager.Instance.HidePanel<BagPanel>();   // ✓
```

泛型是**编译期**确定类型，`typeof(BasePanel).Name` 就是字符串 `"BasePanel"`。约束只保证「是 UIPanel 的子类」，**不保证你传的就是注册时用的那个具体类型**。所以查表失败必须打日志——这就是那条教训的根因。

**补充：泛型与 IL2CPP**。IL2CPP 是 AOT（提前编译），必须在**编译期**就知道要生成哪些泛型实例。所以「运行期用反射构造泛型」在 IL2CPP 下可能失败，需要 `link.xml` 或 `[Preserve]` 来保留代码。这是热更方案绕不开的坑。

## 1.8 集合底层

**结论**：知道扩容和查找的代价，才能选对容器。

**List<T>**

- 内部是一个 `T[]` + `_size`
- `Add` 时若容量不够，**容量翻倍**，并把旧数组整个复制过去
- 所以「知道要放 1000 个」就先 `new List<T>(1000)`，避免多次复制
- `Remove` 是 O(n)（要搬运后续元素）；`RemoveAt` 同理
- 按下标读是 O(1)

**Dictionary<K,V>**

- 内部是 `buckets[]`（哈希桶，存下标）+ `entries[]`（存实际的键值对）
- 查找：算哈希 → 取余落到桶 → 比对 key
- 容量不够时同样翻倍 + 重新分配所有元素（rehash），代价比 List 大
- **不能边遍历边增删**，会抛 `InvalidOperationException`。需要删就先收集 key，遍历完再删

**HashSet<T>**

- 本质是「只有 key 没有 value 的 Dictionary」
- 用途：去重、O(1) 判断「某个东西是否已经处理过」

**你项目里的例子（很典型）**

```csharp
readonly HashSet<Hurtbox> _alreadyHit = new HashSet<Hurtbox>();   // Scripts/Combat/Hitbox.cs
```

「一次挥击每个目标只吃一次」就是靠它实现的：命中后 `_alreadyHit.Add(target)`，判定前 `Contains` 挡掉。用 `List<T>.Contains` 也能做，但那是 O(n) 线性查找，`HashSet` 是 O(1)。判定在 `FixedUpdate` 里每帧跑，目标一多差距就出来了——这个例子面试时很好用。

**另一个例子**

```csharp
readonly Dictionary<Type, UIPanel> _registered = new Dictionary<Type, UIPanel>();
```

按类型存取面板。注意 `Purge()` 里删字典元素时是先收集到 `stale` 列表、再统一删——正是为了绕开「不能边遍历边删」这条限制。

## 1.9 Dictionary 使用细节

**结论**：`TryGetValue` 只查一次，`ContainsKey` + 索引器要查两次。热路径上用前者。

```csharp
// 差：查两次哈希
if (dict.ContainsKey(key))
    var v = dict[key];

// 好：查一次
if (dict.TryGetValue(key, out var v))
    ...
```

**顺带三条实用细节**

1. **`out var` 写法**：C# 7 起可以直接在 `TryGetValue` 里声明变量。
2. **浮点别做 key**：`0.1f + 0.2f != 0.3f`，按值查表会查不到。这正是错题本里「判断浮点数别用 `!=`」的同一个道理。
3. **`GetHashCode` 与 `Equals` 必须成对重写**。只重写一个，自定义类型作 key 时行为会错乱。

**你项目里的例子**

```csharp
UIPanel panel;
if (_registered.TryGetValue(typeof(T), out panel) && panel != null)
    return panel as T;
```

`UIManager.Get<T>()` 就是这么写的——一次查找同时完成「存在吗」和「取出来」。

**面试延伸**：被问「查不到怎么办」，正确答案是**打日志**。`Get<T>()` 查不到返回 `null`，调用方没判空就是 `NullReferenceException`，而报错位置在几十行之外——错题本 009 讲的就是这件事。

## 1.10 GC 与托管堆

**结论**：C# 是托管语言，`new` 出来的对象由 GC 自动回收；回收要暂停程序，所以**游戏里要尽量少产生垃圾（GC Alloc）**。

**基本模型**

- Unity 的 GC 是 **Boehm–Demers–Weiser**（保守式、**非分代**）。
- **常见误解**：「GC 分代（Gen0/1/2）」是传统 .NET 的说法。Unity 用的不是分代 GC，不存在「小对象回收更快」这回事——每次 GC 都要扫描整个托管堆。
- Unity 2019.3 起支持 **Incremental GC**（增量式），把一次大停顿拆成多次小停顿，可在 Player Settings 里开启。
- 触发时机：托管堆增长到阈值时自动触发。也可以用 `System.GC.Collect()` 手动触发，但**游戏里别用**，它会让主线程明显卡一下。

**GC Alloc 的常见来源（背下来，面试必问）**

| 来源 | 例子 |
| --- | --- |
| 字符串拼接 | `"HP: " + hp` 写在 `Update` 里 |
| 装箱 | 值类型传给 `object` / 接口变量 |
| 每次调用返回新数组 | `Physics2D.OverlapBoxAll`、`GetComponentsInChildren` |
| 闭包 | 每帧 `AddListener(() => ...)` |
| LINQ | `list.Where(...).ToList()`，每一步都分配 |
| 协程启动 | `StartCoroutine("方法名")`（字符串形式） |
| `foreach` 遍历接口类型 | 枚举器被装箱 |
| 值类型数组的 `params` | 某些 `Debug.Log` 重载 |

**你项目里的两个真实来源**

```csharp
// 1) Scripts/Combat/HitSpark.cs —— 每次命中 new 一个 GameObject + SpriteRenderer，之后 Destroy
var go = new GameObject("HitSpark");
var sr = go.AddComponent<SpriteRenderer>();

// 2) Scripts/Combat/Hitbox.cs —— OverlapBoxAll 每次调用都新建数组
var overlaps = Physics2D.OverlapBoxAll(center, size, 0f, targetMask);
```

两处都要修（手册里的任务 A2 / A3）。修完之后你就有**真实的优化前后数据**，这是简历上最硬的证据。

**怎么定位**：Profiler → CPU 面板 → 看 `GC Alloc` 列 → 排序 → 展开调用栈找到具体方法。Deep Profile 更细但会拖慢运行。

## 1.11 字符串

**结论**：C# 的 `string` 是**不可变引用类型**。任何「修改」都新建一个字符串，所以循环拼接是灾难。

```csharp
// 差：循环 n 次 → 产生 n 个中间字符串对象
string s = "";
for (int i = 0; i < 100; i++) s += i;

// 好：只分配最终结果（内部缓冲区自动扩容）
var sb = new StringBuilder();
for (int i = 0; i < 100; i++) sb.Append(i);
string result = sb.ToString();
```

**字符串比较**

- `==` 对字符串是**值比较**（内容相同即为真），且是**序数比较**（ordinal），最快。
- `string.Compare(a, b)` 默认按**当前区域性**比较——某些语言环境下会得到意外结果。
- 需要显式指定时用 `string.Equals(a, b, StringComparison.Ordinal)`。

**高频字符串来源**：HUD 每帧拼接 `"血量: " + hp`（应改成数值变化时才更新文本）、每帧 `Debug.Log("x=" + x)`（正式版应关闭）、`tag == "Player"`。

**你项目里的例子**：`UIManager` 里 `panel.GetType().Name + "Root"` 只在创建面板时执行一次，无所谓。但如果 HUD 在 `Update` 里拼血条文字，那就是每帧一次分配——改起来十分钟，改完能讲，值得做。

**面试延伸**：为什么 Unity 里 `tag == "Player"` 慢？因为 `gameObject.tag` 每次访问都会把内部索引转成字符串。热路径应该用 `CompareTag("Player")`——它直接比索引，不分配。

## 1.12 协程原理

**结论**：协程不是线程。它是**编译器帮你生成的一个状态机类**，由 MonoBehaviour 每帧驱动着往前走。

**编译器做了什么**

```csharp
// 你写的
IEnumerator Fade()
{
    yield return new WaitForSeconds(1f);
    Debug.Log("一秒后");
}
```

编译器会生成一个实现了 `IEnumerator` 的类，大致等价于：

```csharp
class FadeStateMachine : IEnumerator
{
    int _state = 0;
    public bool MoveNext()
    {
        switch (_state)
        {
            case 0: _state = 1; return true;   // 第一次：返回一个「等 1 秒」的指令
            case 1: Debug.Log("一秒后"); return false;   // 第二次：执行剩余代码，结束
        }
    }
    public object Current { get; }   // 就是 yield return 出来的那个东西
}
```

Unity 每帧调用 `MoveNext()`，并根据 `Current` 决定「什么时候再调下一次」。所以协程**始终在主线程**，一段代码运行期间不会被别处插进来。

**常用 yield 指令**

| 写法 | 何时继续 |
| --- | --- |
| `yield return null` | 下一帧（`Update` 之后） |
| `yield return new WaitForFixedUpdate()` | 下一个物理帧，在 `FixedUpdate` 之后 |
| `yield return new WaitForEndOfFrame()` | 当前帧渲染结束后 |
| `yield return new WaitForSeconds(t)` | **受 `timeScale` 影响**（你 `Time.timeScale = 0` 时它不会继续） |
| `yield return new WaitForSecondsRealtime(t)` | 用非缩放时间，**不受 `timeScale` 影响** |
| `yield return someCoroutine` | 等嵌套的协程跑完 |
| `yield break` | 提前结束 |

**协程的三条限制**

1. **不能 `try-catch` 包住 `yield`**：「在协程里捕获异常并继续」是不行的（C# 编译器直接禁止 `yield return` 出现在 `catch` 里）。协程里抛出的异常会打断该协程。
2. **随宿主而死**：`MonoBehaviour` 被禁用或销毁，它启动的所有协程立即停止。这对你的项目很重要——`UIManager` 是 `DontDestroyOnLoad`，所以它的加载协程不会被场景切换干掉。
3. **不返回值**：要拿协程的返回值得靠回调或字段。

**你项目里的例子**

```csharp
IEnumerator LoadSceneRoutine(string sceneName, string loadingLabel)
{
    CloseAll();
    GamePause.Set(false);
    ShowLoading(loadingLabel);

    var operation = SceneManager.LoadSceneAsync(sceneName, LoadSceneMode.Single);
    while (!operation.isDone) yield return null;   // 每帧检查一次，不阻塞主线程
    yield return null;                             // 再等一帧，等新场景的对象 Awake 完
    HideLoading();
}
```

面试可以这么讲：这里用 `yield return null` 轮询 `isDone` 而不是 `yield return operation`，是因为要**每帧检查 `operation` 是否为 null**（场景不在 Build Settings 里时 `LoadSceneAsync` 返回 null）。最后那个 `yield return null` 是为了让新场景的对象完成初始化再关掉遮罩，避免闪一帧黑屏。

**为什么会 GC**：`StartCoroutine(方法名字符串)` 走反射，开销大且会分配；`StartCoroutine(Routine())` 会为每次调用新建一个状态机对象。前者应一律避免。

## 1.13 async / await 与 UniTask

**结论**：协程、`Task`、`UniTask` 是三种异步方案。游戏里绝大多数场景协程够用；需要「返回值」和「异常处理」时用 `UniTask`。

| | 协程 | Task / async-await | UniTask |
| --- | --- | --- | --- |
| 线程 | 主线程 | 默认线程池（**不能碰 Unity API**） | 主线程 |
| 返回值 | 没有 | 有 | 有 |
| 异常处理 | 差 | 好（`try-catch` 可用） | 好 |
| GC | 每次启动分配状态机 | 分配较多 | 极少（值类型任务） |
| 取消 | `StopCoroutine` | `CancellationToken` | `CancellationToken` |
| 依赖 | 内置 | 内置 | 第三方包（Cysharp/UniTask） |

**`Task` 在 Unity 里的坑**

```csharp
async void BadExample()          // async void：异常无法被外部捕获，会直接崩
{
    await Task.Delay(1000);
    transform.position = Vector3.zero;   // ✗ 可能不在主线程！Unity API 不允许
}
```

`await Task.Delay(...)` 默认回到线程池线程，此时访问 `transform` 会抛异常。要回主线程得配合 `SynchronizationContext`——这正是 `UniTask` 存在的理由：它基于 Unity 的 **PlayerLoop**，全程在主线程，零分配。

**什么时候真的需要异步方案**：加载资源（`Addressables` 全程异步）、网络请求、等待多个条件同时满足。

## 1.14 static 生命周期

**结论**：`static` 字段属于**类型**不属于实例，生命周期跟随「程序集被加载的时间」。在 Unity 编辑器里，这带来一个非常隐蔽的坑。

```csharp
public class CombatTuning : ScriptableObject
{
    static CombatTuning _current;
    public static CombatTuning Current
    {
        get
        {
            if (_current == null) _current = Resources.Load<CombatTuning>("CombatTuning");
            return _current;
        }
    }
}
```

**Domain Reload 是什么**：默认情况下，每次进入 Play 模式，Unity 会重新加载整个 AppDomain，所有 `static` 字段被重置为默认值。所以你在 Play 模式里改了 `CombatTuning.asset`，`_current` 引用的是老对象——但因为你在 Inspector 里改的就是那个对象，通常看不出问题。

**坑在哪**：项目设置里有 `Enter Play Mode Options`，可以关掉 Domain Reload 来加快进入 Play 的速度。一旦关掉：

- `static` 字段**不会重置**。`_current` 会保留上一次 Play 时的引用，你改了 asset 却发现没生效，或者引用了已被销毁的对象。
- 事件订阅也不会清空，会累积重复订阅——同一个回调被调用两次。

**正确的解法**：显式重置。

```csharp
[RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.SubsystemRegistration)]
static void ResetStatics()
{
    _current = null;
}
```

`SubsystemRegistration` 在每次进入 Play 时都会执行，即使关闭了 Domain Reload。**你的项目里有好几个静态单例（`UIManager._instance`、`HitStopManager.Instance`、`CombatTuning._current`），如果打算关闭 Domain Reload 提速，这几个都要加重置方法。**

**面试延伸**：`static` 还意味着「跨场景共享状态」。你的 `HitStopManager` 是场景内单例，`UIManager` 是 `DontDestroyOnLoad` 的常驻单例——这两种单例的失效边界不同，值得说清楚。

# 第二部分 · Unity 引擎机制

## 2.1 生命周期完整顺序

**结论**：背下这张表，它是 Unity 面试的第一道门槛。

```
加载 / 实例化
  Awake            对象创建时调用一次（即使脚本组件被禁用也会调用）
  OnEnable         每次对象被启用时调用
  Start            第一帧 Update 之前调用一次（仅在启用状态下）

每帧循环（顺序固定）
  FixedUpdate      固定时间步长，物理与帧驱动逻辑
  物理模拟         物理引擎内部步进
  OnTriggerXXX / OnCollisionXXX    物理回调
  Update           每帧一次
  协程 yield null 恢复 / yield WaitForFixedUpdate
  LateUpdate       所有 Update 之后，相机跟随通常放这里
  渲染
  OnRenderObject / OnGUI / 协程 WaitForEndOfFrame

销毁
  OnDisable        （禁用或销毁前）
  OnDestroy        对象被销毁时
  OnApplicationQuit 应用退出时
```

**几个必须知道的细节**

- `FixedUpdate` 在一帧内可能执行 **0 次、1 次或多次**——取决于帧耗时和固定步长。
- `Awake` 在所有对象上先于任何 `Start` 执行；`Start` 的执行顺序在对象之间不保证。
- `OnEnable` 在 `Awake` 之后、`Start` 之前，并且对象每次被重新启用都会再调用。
- 对象被销毁时，`OnDisable` → `OnDestroy` 依次调用。

**你项目里的例子**

```csharp
void Awake()      // PlayerCombat：缓存 CombatTuning、订阅 Health 事件、初始化血量体力
void OnDestroy()  // PlayerCombat：取消订阅
void FixedUpdate()// PlayerCombat / AttackRunner / Hitbox / Stamina / Stagger 全部逻辑
```

为什么初始化和订阅放在 `Awake` 而不是 `Start`？因为 `Start` 在第一个 `Update` 之前才跑，而 `FixedUpdate` 可能比 `Start` 更早执行——放在 `Awake` 更保险。**这是你能讲出来的具体理由，不是背来的。**

## 2.2 Awake / OnEnable / Start 的区别

**结论**：`Awake` 管「我自己初始化」，`OnEnable` 管「我每次被打开时要做什么」，`Start` 管「我准备好之后的第一次」。

| | 调用次数 | 组件被禁用时 | 依赖其他对象时 |
| --- | --- | --- | --- |
| `Awake` | 一次 | **仍然调用** | 可能还没 Awake，别依赖别人 |
| `OnEnable` | 每次启用 | 不调用 | 同上 |
| `Start` | 一次 | 不调用 | 别人的 `Awake` 已跑完，相对安全 |

**实战判断**

- 自己内部的状态初始化（缓存引用、设默认值）→ `Awake`
- 需要别人已经初始化好才能做的事 → `Start`
- 对象池里反复启用的对象，每次启用都要重置的东西 → `OnEnable`

**对象池的关键**：池化的对象被回收再利用时，`Awake` 和 `Start` **不会**再调用，只有 `OnEnable` 会。所以池化对象的「重置」逻辑必须写在 `OnEnable` 里，或者由一个显式的 `ResetForReuse()` 方法处理。**这是任务 A2 对象池最容易漏的地方**——不重置，第二个火花会带着第一个的残留颜色和缩放。

---

## 2.3 Script Execution Order

**结论**：默认情况下，不同脚本之间的执行顺序是**未定义**的，只保证 `Awake` 早于 `Start`、`FixedUpdate` 早于 `Update` 这类阶段顺序。需要确定性时，显式设置。

**两种做法**

1. Project Settings → Script Execution Order：把某个类的顺序数值调小（更早）或调大（更晚）。
2. 代码里用 `[DefaultExecutionOrder(-100)]` 特性。

```csharp
[DefaultExecutionOrder(-100)]     // 负值 = 更早执行
public class PrototypeBootstrap : MonoBehaviour { ... }
```

**什么时候真的需要**

- 管理器必须在其他对象之前就绪（比如 `PrototypeBootstrap` 要先建好场景对象）
- 相机跟随必须晚于角色移动（更推荐的做法是用 `LateUpdate` 而不是改执行顺序）

**你项目里的证据**：`Scripts/Core/PrototypeBootstrap.cs` 是原型场景的入口，如果它需要在其他对象之前跑，就应该有明确顺序；如果只是靠命名巧合，那是隐患。

**最佳实践**：能用 `LateUpdate`、协程、事件解决的就不要动执行顺序——执行顺序是全局的、难追踪的隐式依赖。

## 2.4 时间系统

**结论**：五个时间相关属性，各有用途，混用就出错。

| 属性 | 含义 |
| --- | --- |
| `Time.deltaTime` | 上一帧到这一帧经过的时间，**受 `timeScale` 影响** |
| `Time.unscaledDeltaTime` | 同上，但**不受 `timeScale` 影响** |
| `Time.fixedDeltaTime` | 物理步长（默认 0.02 秒）。受 `timeScale` 影响，所以 `timeScale=0` 时物理停止 |
| `Time.timeScale` | 时间缩放。0 = 完全暂停，0.5 = 半速 |
| `Time.maximumDeltaTime` | 单帧最大耗时上限（默认 0.333），防止卡顿时物理"追帧"雪崩 |

**关键关系**

```csharp
Time.deltaTime ≈ Time.unscaledDeltaTime * Time.timeScale
```

所以当你把 `Time.timeScale = 0` 时：

- `Update` **仍然会执行**（它不依赖 timeScale 决定跑不跑）
- 但 `Time.deltaTime` 变成 0，所以 `transform.position += v * Time.deltaTime` 纹丝不动
- `FixedUpdate` **完全不执行**（物理步进被完全停下）
- `yield return new WaitForSeconds(1)` 永远不会到时间
- `yield return new WaitForSecondsRealtime(1)` 照常计时
- 动画（Animation / Animator）停止推进

**你项目里的例子（非常值得讲）**

```csharp
// Scripts/Core/HitStopManager.cs
if (_framesRemaining > 0)
{
    if (!_frozen) { _frozen = true; Time.timeScale = 0f; }
    _frameAccumulator += Time.unscaledDeltaTime;   // ← 关键：用非缩放时间倒计时
    while (_frameAccumulator >= _frameUnit && _framesRemaining > 0) { ... }
}
```

冻结期间 `Time.deltaTime` 是 0，如果这里用 `deltaTime` 倒计时，hitstop 永远结束不了——游戏会死锁。所以必须用 `unscaledDeltaTime`。**这是一个能直接讲给面试官的设计细节。**

**⚠️ 你项目里的一个真实偏差（重要）**

```
ProjectSettings/TimeManager.asset:   Fixed Timestep: 0.02      ← 50 Hz
Assets/Scripts/Combat/AttackProfile.cs:  [Header("帧数（60fps 基准）")]
```

`FixedUpdate` 的步长是 **0.02 秒（50fps）**，但你的招式数据注释写的是「60fps 基准」。这意味着 `startupFrames = 8` 实际是 8 × 20ms = **160ms**，而不是你心里想的 8 × 16.7ms = 133ms——**所有招式都比设计意图慢了约 20%**。

两种修法（选一种，别两个都改）：

1. 把 `Project Settings → Time → Fixed Timestep` 改成 `0.0166667`（即 1/60），让「1 帧 = 1/60 秒」与注释一致。
2. 保留 0.02，把注释和调参基准改成「50fps 基准」。

**推荐第 1 种**，因为动作游戏社区和绝大多数帧数据表都以 60fps 为基准，你以后参考别人的数据表时不用换算。

> 这条要写进《错题本.md》——它是「注释和代码对不上」的典型，正是你自检清单第 8 条。

## 2.5 为什么用 FixedUpdate 做战斗逻辑

**结论**：因为战斗逻辑要和物理同频。物理在固定步长里步进，如果逻辑跑在 `Update`（帧率相关），就会出现「帧率越高，判定越细」的不一致。

| | `Update` | `FixedUpdate` |
| --- | --- | --- |
| 频率 | 跟帧率走（可能 30 / 60 / 144） | 固定 50 Hz（默认） |
| 一帧内执行次数 | 恰好一次 | 0 次、1 次或多次 |
| 与物理的关系 | 在物理之后 | 与物理同步 |
| 适合放什么 | 输入采集、相机跟随、UI 刷新、表现层 | 移动、攻击判定、状态机、伤害结算 |

**为什么物理必须是固定步长**：物理模拟用数值积分，步长不同就会得到不同结果。同一场战斗，144Hz 的机器和 30Hz 的机器如果判定结果不一样，对竞技游戏是致命的。

**你的项目做得对的地方**：`PlayerCombat`、`AttackRunner`、`Hitbox`、`Stamina`、`Stagger`、`BossController` 全部在 `FixedUpdate` 里跑，而且用**帧计数**而不是时间累加。

```csharp
_stateFrame++;
if (_stateFrame >= tuning.dodgeFrames) { ... }
```

帧计数的好处：

- **确定性**：同样的输入序列 → 同样的结果，与帧率无关
- **可复现**：录下输入就能精确重放，方便查 bug
- **好调参**：招式表就是整数，和动画帧对得上

如果用 `Time.deltaTime` 累加，浮点误差会累积，且帧率变化会让判定漂移。**这是你能主动讲出来的、超出"背八股"层次的观点。** 讲完可以接一句：「这也是帧同步方案的前提——所有逻辑必须确定性。」

**代价也要会说**：帧驱动意味着「帧」是硬编码的时间单位，改物理步长会改变所有招式手感；而表现层（特效、UI）仍然用 `Update` + `deltaTime`，两者之间需要转换（比如 `frames * Time.fixedDeltaTime` 求出秒数）。

## 2.6 物理 2D

**结论**：Rigidbody2D 决定「这个物体怎么运动」，Collider2D 决定「它的形状」，Layer 决定「谁和谁发生关系」。

**Rigidbody2D 的三种 Body Type**

| 类型 | 受重力/力 | 会移动 | 典型用途 |
| --- | --- | --- | --- |
| Dynamic | 是 | 是 | 玩家、会掉落的箱子 |
| Kinematic | 否 | 脚本或 `MovePosition` 驱动 | 移动平台、纯逻辑物体 |
| Static | 否 | 否 | 地形、墙 |

一条实用经验：**大量不动的碰撞体用 Static；纯逻辑、不需要物理反馈的用 Kinematic**。玩家通常用 Dynamic + 自己控制速度。

**你项目里的做法（值得讲）**

```csharp
// PlayerMotor / PlayerCombat 直接改 velocity，而不是 AddForce
var velocity = Motor.Body.velocity;
Motor.Body.velocity = new Vector2(_dodgeDirection * tuning.dodgeSpeed, velocity.y);
```

为什么直接赋值 `velocity` 而不用 `AddForce`？因为**动作游戏要的是精确、可预测的位移**，`AddForce` 是加速度语义、受质量和阻力影响，手感不可控。「手感优先用速度，物理感优先用受力」——这句话比背 API 有用。

**参数与体感的关系（面试常问）**

| 参数 | 影响 |
| --- | --- |
| Gravity Scale | 重力倍率。你项目里设成 3.6，让跳跃更"干脆"（加大下落感） |
| Velocity Iterations | 速度迭代次数，越大越准越耗性能 |
| Position Iterations | 位置迭代次数 |
| Interpolate | 物理帧与渲染帧之间的插值，**开启后画面不再抖动** |
| Collision Detection | Discrete / Continuous，快速物体用 Continuous 防穿透 |

**Layer 碰撞矩阵**：`Project Settings → Physics 2D → Layer Collision Matrix`。即使代码里判了团队，也建议用 Layer 把「玩家攻击盒」和「玩家受击盒」分开，减少无意义的物理查询。

**你项目里的两个设置（可能踩坑）**

```
Physics2DSettings.asset:
  m_QueriesStartInColliders: 1      ← 查询起点在碰撞体内部时，也能检测到它
  m_AutoSyncTransforms: 0           ← 改 Transform 不会立即同步给物理系统
```

- 第一项为 1 是好消息：`Hitbox` 的查询起点落在目标受击盒内部时仍然能命中。
- 第二项为 0 意味着：如果你在同一次循环里先改 `transform.position` 再立刻做物理查询，物理系统看到的还是旧位置。**你的 `Hitbox` 用的是 `owner.position` 配合 `Rigidbody2D` 驱动，一般没问题，但这是个要记住的隐患。**

## 2.7 触发器 vs 物理查询

**结论**：触发器是「物理系统主动通知你」，查询是「你主动问物理系统」。命中判定更适合查询。

| | `OnTriggerEnter2D` / `OnTriggerStay2D` | `Physics2D.OverlapBox` 系列 |
| --- | --- | --- |
| 方向 | 事件推给你 | 你主动去问 |
| 时序 | 由物理引擎调度，顺序不完全可控 | 你自己决定在哪一步查 |
| 可控性 | 判定盒开合要靠启停 Collider | 直接传参数，随时可查 |
| 调试 | 只能看 `OnDrawGizmos` 或运行时可视化 | 可用 Gizmos 画出来，调参数所见即所得 |
| 性能 | 常驻的碰撞体都在参与；`Stay` 每物理帧都回调 | 只在需要的帧调用 |

**你项目里的做法**

```csharp
// Scripts/Combat/Hitbox.cs
var overlaps = Physics2D.OverlapBoxAll(center, size, 0f, targetMask);
```

为什么这么设计（面试可以直接照这个说）：

1. **时序确定**：出招时判定盒什么时候开、什么时候关，由 `AttackRunner` 的帧数据说了算，不依赖物理引擎的调度顺序。
2. **不用启停哪个 Collider**：判定盒是一个数学矩形，不是场景里的碰撞体，省掉了「开关触发器的时机 bug」这一类问题。
3. **所见即所得**：`OnDrawGizmosSelected` 把判定盒直接画出来，拖数值立刻看到范围变化——这在调动作手感时是刚需。

**代价**：`OverlapBoxAll` 每次返回新数组 → GC（见 1.10）。修法（任务 A3）：

```csharp
readonly List<Collider2D> _results = new List<Collider2D>(8);
readonly ContactFilter2D _filter = new ContactFilter2D();

void Awake()
{
    _filter.useLayerMask = true;
    _filter.layerMask = targetMask;
    _filter.useTriggers = true;
}

void FixedUpdate()
{
    if (!_active) return;
    int count = Physics2D.OverlapBox(BoxCenter, BoxSize, 0f, _filter, _results);
    for (int i = 0; i < count; i++) { var col = _results[i]; /* ... */ }
}
```

再把 `col.GetComponentInParent<Hurtbox>()` 的结果缓存进 `Dictionary<Collider2D, Hurtbox>`，整个判定就零分配了。

## 2.8 序列化特性

**结论**：Unity 的 Inspector 序列化有自己的一套规则，和 C# 的「可访问性」不是一回事。

| 特性 | 作用 |
| --- | --- |
| `[SerializeField]` | 把 private 字段暴露给 Inspector 并序列化 |
| `[HideInInspector]` | 公开字段但不显示在 Inspector（仍被序列化） |
| `[Serializable]` | 让自定义 class / struct 可以被序列化（**必须加**，否则嵌在组件里是空的） |
| `[Header("...")]` | Inspector 分组标题 |
| `[Tooltip("...")]` | 悬停提示 |
| `[Range(0,1)]` | 变成滑条 |
| `[NonSerialized]` | 不序列化（对 public 字段生效） |

**能被序列化的类型**

- 基本类型：`int` `float` `bool` `string` `enum`
- Unity 内建类型：`Vector2/3` `Color` `AnimationCurve` `Rect` 等
- 以上类型的数组和 `List<T>`
- 加了 `[Serializable]` 的自定义 class / struct
- 继承 `UnityEngine.Object` 的引用（`GameObject`、`Component`、`ScriptableObject` 等）

**不能序列化的**：`Dictionary`、接口、`static` 字段、`null` 的 `List<T>`（Unity 会把它变成空列表）、多态引用（父类型字段存子类实例会退化成父类）。这最后一条很重要——**想做多态序列化必须靠 `SerializeReference`**。

**你项目里的例子**

```csharp
[Serializable]
public class AttackProfile { ... }     // 因为是 class，必须加 [Serializable] 才能嵌进 CombatTuning

[HideInInspector] public IDamageGuard guard;   // 接口不能序列化，所以运行时在 Resolve() 里赋值
```

`Hurtbox.guard` 标 `[HideInInspector]` + 运行期 `FindInterface<IDamageGuard>()` 赋值——**正因为接口类型无法被 Inspector 序列化**。这个细节面试时能解释清楚，说明你真的懂序列化规则，而不是照抄。

**`[HideInInspector]` 与 private 字段的坑**：`[HideInInspector]` 只影响 Inspector 显示，字段仍然会被序列化并存进场景文件。所以「不想让别人在 Inspector 改」和「不想被存进文件」是两件事，后者要用 `[NonSerialized]`。

## 2.9 ScriptableObject

**结论**：ScriptableObject 是「存在工程里的数据资产」。它不属于任何场景，多个场景和对象共享同一个实例。

| | MonoBehaviour | ScriptableObject |
| --- | --- | --- |
| 存在哪 | 挂在 GameObject 上 | 独立的 `.asset` 文件 |
| 生命周期 | 随场景对象 | 随资源加载，跨场景存在 |
| 能否放逻辑 | 能（有 Update） | **不建议**（没有固定的 Update 时机） |
| 典型用途 | 行为 | 配置数据、共享数据、事件通道 |

**为什么配置数据要用 SO 而不是 static class 或 JSON**

- 编辑体验：Inspector 里可视化编辑，改完立刻生效，不用重新编译
- **Play 模式下能实时改**：你在 Play 模式调整 `CombatTuning.asset`，效果立刻反映到运行中的游戏——这是动作游戏调手感的关键效率工具
- 可以被其他资产引用（比如 Boss 引用一套招式表）
- 脱离代码：策划也能改

**你项目里的例子**

```csharp
[CreateAssetMenu(fileName = "CombatTuning", menuName = "ZMZZ/Combat Tuning")]
public class CombatTuning : ScriptableObject
{
    public static CombatTuning Current
    {
        get
        {
            if (_current == null) _current = Resources.Load<CombatTuning>("CombatTuning");
            return _current;
        }
    }
}
```

这个设计的三个可讲之处：

1. `CreateAssetMenu` 让美术/策划能自己新建和复制配置（比如做「困难模式」只需复制一份改数值）。
2. `Resources.Load` 一份 + static 缓存，避免每次访问都查文件。
3. 兜底：找不到 asset 就 `CreateInstance` 用内存默认值，**游戏不会因为缺配置而崩溃**。这是能主动讲出来的健壮性设计。

**SO 的坑**

- 编辑器里改了 SO 的值会**永久保存到 asset 文件**（不是运行时临时改）。这点常让人意外：Play 模式调完手感，退出后数值留下来了——这既是优点也是风险（记得用 git 看 diff）。
- 打包后 SO 是只读的，**不能用来存运行期数据**（存档要用 JSON + `persistentDataPath`）。
- `static` 缓存 + 关闭 Domain Reload 的坑见 1.14。

## 2.10 Prefab 与 Instantiate

**结论**：Prefab 是「对象模板」，`Instantiate` 是「按模板创建一个副本」。实例化有真实开销，高频创建必须池化。

**`Instantiate` 的开销来自哪**

- 分配新的托管对象和 GameObject
- **深复制整个组件树和序列化数据**（Prefab 越大越慢）
- 所有组件的 `Awake` / `OnEnable` 依次执行
- 如果 Prefab 里有 `SpriteRenderer`，还会触发渲染相关注册

**Prefab 实用知识**

| 概念 | 说明 |
| --- | --- |
| Prefab Variant | 基于一个 Prefab 派生变体，改基类会同步到变体 |
| Nested Prefab | Prefab 里嵌 Prefab，适合组合式搭建 |
| Prefab Mode | 单独打开 Prefab 编辑，避免"改实例没改模板" |
| Override | 实例上改的东西是 override，会覆盖模板 |
| Apply / Revert | 把实例改动应用回模板 / 撤销 |

**实例化时注意**

- `Instantiate(prefab, position, rotation, parent)` 一步到位，比创建后再设父物体好（避免一次多余的坐标变换计算）
- 循环里批量创建要小心：每帧创建几十个对象会造成明显峰值
- 池化对象不要用 `Instantiate`/`Destroy`，用 SetActive 或队列管理

**你项目里的例子**

```csharp
// Scripts/Combat/HitSpark.cs
var go = new GameObject("HitSpark");
var sr = go.AddComponent<SpriteRenderer>();
```

这里是**手工 new + AddComponent**，比 `Instantiate` 一个 Prefab 更慢（`AddComponent` 每次都要走组件注册）。正确的方向是两件事一起做：

1. 做一个 `HitSpark.prefab`；
2. 用 `ObjectPool<HitSpark>` 管理，每次命中从池里取、设置位置和颜色、`SetActive(true)`。

这样不仅消除 GC，连 `AddComponent` 的开销也没了。任务 A2 就是这个。

## 2.11 资源加载

**结论**：`Resources` 是原型期的便利工具，正式项目应该用 Addressables。

| | Resources | Addressables | AssetBundle |
| --- | --- | --- | --- |
| 加载方式 | `Resources.Load<T>("路径")` | 异步/同步，按地址 | 手动管理依赖 |
| 打包 | **全量打进包，无法剔除** | 按需打包，独立可分 | 手动指定 |
| 卸载 | 只能 `Resources.UnloadUnusedAssets`（全量扫描） | 引用计数，精确卸载 | 手动 |
| 热更 | 不支持 | 支持 | 支持 |
| 路径 | 字符串硬编码，改目录就崩 | 地址可配置 | — |

**`Resources` 的三个缺点（面试标准答案）**

1. **全部打进包体**：`Resources` 文件夹里的东西无论用不用都会进最终包，且无法被依赖剔除。
2. **无法精确卸载**：只有 `UnloadUnusedAssets`，一次全量扫描，卡顿明显。
3. **字符串路径**：重命名或移动文件不会报编译错，运行时才发现，且容易重复加载。

**加载方式对比**

```csharp
// 同步：会卡住主线程，大资源尤其明显
var asset = Resources.Load<GameObject>("Prefabs/Enemy");

// Addressables 异步：不卡帧
var handle = Addressables.InstantiateAsync("Enemy");
await handle.Task;

// 预加载 + 释放
var handle = Addressables.LoadAssetAsync<CombatTuning>("CombatTuning");
yield return handle;
Addressables.Release(handle);
```

**你项目里的现状与建议**：`CombatTuning.Current` 用 `Resources.Load`——**这在原型期完全没问题，而且值得保留**，因为它让 `CombatTuning` 不需要在场景里挂引用。面试时主动说清「原型期用 Resources 换开发速度，正式项目会迁到 Addressables，理由是包体和精确卸载」——**这句话本身就是加分的**，比假装一开始就该用 Addressables 更真实。

**延伸知识**：引用计数。Addressables 里同一个资源被加载两次只会有一份实例，`Release` 一次计数减一，减到 0 才真正释放。这也是为什么必须成对 `Load` / `Release`——和事件订阅必须 `+=` / `-=` 是同一类思维。

## 2.12 对象池

**结论**：对象池 = 把「用完就销毁」改成「用完还回去，下次接着用」。目标是消除高频创建/销毁带来的 GC 和 CPU 峰值。

**什么时候该用**

- 子弹、特效、伤害数字、音效播放器、敌人（大量同类）
- 判断标准：**同一类东西在一秒内会创建多次**

**Unity 自带的对象池**

```csharp
using UnityEngine.Pool;

ObjectPool<HitSpark> _pool;

void Awake()
{
    _pool = new ObjectPool<HitSpark>(
        createFunc:     () => Instantiate(_prefab),      // 池空时怎么创建
        actionOnGet:    s => s.gameObject.SetActive(true),
        actionOnRelease:s => s.gameObject.SetActive(false),
        actionOnDestroy:s => Destroy(s.gameObject),
        collectionCheck: true,      // 重复释放时报错（开发期建议开）
        defaultCapacity: 16,
        maxSize: 64                 // 超过上限的会被真正销毁，防止池无限增长
    );
}
```

**池化对象必须重置的三件事（面试会追问）**

1. **状态**：计时器、速度、颜色、缩放、血条。不重置 → 第二个特效用第一个的残留颜色。
2. **引用**：指向外界的回调、事件订阅、父物体。不清理 → 泄漏或错误调用。
3. **激活状态**：归还时 `SetActive(false)`。注意 `OnEnable` 会再次触发，重置逻辑放这里最稳。

**三个常见陷阱**

| 陷阱 | 后果 |
| --- | --- |
| 归还后还被外部引用 | 对象已被复用，引用方拿到的是"别人的"对象 |
| 忘记重置状态 | 视觉/逻辑残留 |
| 池没有上限 | 内存只增不减，等于没优化 |

**你项目里的应用（任务 A2）**

```csharp
// 现在：HitSpark.Spawn 每次都 new + AddComponent，结束后 Destroy
// 目标：
public static void Spawn(Vector2 position, Color color, float startScale, float endScale, float life)
{
    var spark = _pool.Get();
    spark.Init(position, color, startScale, endScale, life);   // Init 里做完所有重置
}
// 生命周期结束时 _pool.Release(this) 而不是 Destroy(gameObject)
```

**验收方式**：Profiler 里连续命中 100 次，`GC Alloc` 为 0。这就是简历上「基于对象池消除 GC Alloc」的证据。

## 2.13 UGUI 基础

**结论**：UGUI 的四件套——`Canvas` 提供绘制容器，`CanvasScaler` 做分辨率适配，`GraphicRaycaster` 负责点击检测，`EventSystem` 负责事件派发。

| 组件 | 职责 |
| --- | --- |
| `Canvas` | 绘制容器与层级（`sortingOrder`） |
| `CanvasScaler` | 分辨率适配（`ScaleWithScreenSize` + 参考分辨率） |
| `GraphicRaycaster` | 把鼠标/触摸位置转成 UI 元素 |
| `EventSystem` | 派发点击、拖拽、键盘导航事件（**每个场景都需要一个**） |

**你项目里的例子**

```csharp
void BuildLayers()
{
    var go = new GameObject(layer + " Layer", typeof(RectTransform), typeof(Canvas),
                            typeof(CanvasScaler), typeof(GraphicRaycaster));
    canvas.renderMode = RenderMode.ScreenSpaceOverlay;
    canvas.sortingOrder = BaseSortingOrder + i * 100;
    scaler.uiScaleMode = CanvasScaler.ScaleMode.ScaleWithScreenSize;
    scaler.referenceResolution = new Vector2(1920f, 1080f);
    scaler.matchWidthOrHeight = 0.5f;
}

void EnsureEventSystem()
{
    if (FindObjectOfType<EventSystem>() != null) return;
    var go = new GameObject("[EventSystem]", typeof(EventSystem), typeof(StandaloneInputModule));
    DontDestroyOnLoad(go);
}
```

**这段代码里每一个设计都值得讲**

1. **四层 Canvas 而不是一个**：`Background / Normal / Popup / Toast` 各一个 Canvas，`sortingOrder` 相差 100。为什么？因为 Canvas 是**重建（rebuild）的最小单位**——任何一个子元素变化都会导致整块 Canvas 重新生成网格。分层之后，改血条不会连累弹窗。
2. **`EnsureEventSystem`**：这就是错题本 010 那条教训——「按钮点不动，第一反应查 EventSystem」。你把它做成了自动创建，一劳永逸。
3. **`DontDestroyOnLoad`**：UI 管理器常驻，换场景不丢界面系统。
4. **`ScreenSpaceOverlay`**：不依赖相机，不需要额外配置。

**`ScreenSpaceOverlay` vs `ScreenSpaceCamera` vs `WorldSpace`**

| 模式 | 特点 |
| --- | --- |
| Overlay | 永远画在最上层，不受相机影响，性能最好 |
| ScreenSpaceCamera | 受相机参数影响，可被 3D 物体遮挡 |
| WorldSpace | UI 在 3D 世界里（血条、对话框） |

## 2.14 UGUI 性能

**结论**：UGUI 的性能问题几乎都来自**重建（Rebuild）**和**布局（Layout）**。

**重建机制**

- 任何 UI 元素的**顶点数据变化**（位置、大小、颜色、文字内容）都会把它所在的 Canvas 标记为 dirty
- Canvas 在下一帧重新生成整块网格（`Canvas.BuildBatch`）
- **一个 Canvas 里元素越多，每次重建越贵**

**优化手段（按性价比）**

| 手段 | 说明 |
| --- | --- |
| 动静分离 | 频繁变动的元素（血条、计时、伤害数字）放独立 Canvas |
| 避免 Layout 组件 | `HorizontalLayoutGroup` 等布局组件在元素变化时触发重排，动态列表里代价高 |
| `SetActive` 取舍 | 隐藏元素用 `SetActive(false)` 可减少重建，但反复开关会触发 OnEnable 开销 |
| 不用 `Text` 用 TMP | 见 2.15 |
| 减少 Overdraw | 半透明大图层次叠加 |
| Canvas 分层 | 就是你 `UIManager` 的四层 |

**一个典型的性能事故**：把血条文字放在主 Canvas 上，每帧 `text = "HP: " + hp`。结果是每帧重建整个界面 + 每帧产生字符串垃圾。修法：血条放独立 Canvas；只在数值真正变化时才更新文本；用 `StringBuilder` 或直接格式化整数。

**面试可以这么答**：「UGUI 的瓶颈通常不在绘制，而在重建。所以我会把频繁变化的 UI 拆到独立 Canvas，并避免在布局组里放动态元素。」

## 2.15 TextMeshPro

**结论**：TMP 是 UGUI 文本的现代方案，用 SDF（有向距离场）渲染，任意字号都清晰；代价是**字体资产必须包含你要用到的字形**。

| | 旧 `Text` | TextMeshPro |
| --- | --- | --- |
| 清晰度 | 位图，放大糊 | SDF，任意字号清晰 |
| 富文本 | 弱 | 强（描边、阴影、渐变、字距） |
| 性能 | 每次文本变化重建整块纹理（昂贵） | 更省 |
| 中文 | 需自带字体 | **必须烘焙成字体资产** |

**中文的两条路**

1. **静态字体资产**：用 Font Asset Creator 把常用汉字的字形烘焙进去。体积小、性能好，但**没烘焙的字会显示成方框或缺字**。
2. **动态字体资产**（Dynamic）：运行时按需生成字形，不会缺字，但首次显示某个字时有开销，且需要图集空间。

**你项目里的做法（错题本里的坑）**

```csharp
// UITheme.DefaultFont 会自动从系统字体里挑中文字体（微软雅黑等）
// 教训：新增文字别自己写 GetBuiltinResource<Font>
```

这条已经写进你的自检清单了：「显示文字前，先确认这个字体里有这些字形」。TMP 默认字体只有英文——这是 Unity 新手最常踩的坑之一，你踩过了并且记下来了，**这就是面试素材**。

**延伸**：TMP 的 `SetText` 系列重载（`SetText(int)` 等）不产生字符串分配，而 `text = "HP: " + hp` 会。高频刷新的数字（血量、计时、伤害数字）应该用 `SetText`。

## 2.16 URP 与 2D 渲染

**结论**：URP（Universal Render Pipeline）是 Unity 的通用可编程渲染管线。2D 项目用 URP 的 2D Renderer，能得到 Light2D 和 2D 阴影等能力。

| 管线 | 特点 | 适用 |
| --- | --- | --- |
| Built-in | 老管线，文档最多，扩展靠 `OnRenderImage` 等 | 老项目 |
| URP | 轻量、跨平台、可视化配置、可自定义 Renderer Feature | 移动端、2D、独立游戏 |
| HDRP | 高质量，重 | 3A、PC 高画质 |

**Sprite-Lit 与全局光（你的错题本第 2 条）**

```
URP 2D 场景必须有 Light2D 且设为 Global
否则 Sprite-Lit 材质全部渲染成黑色
```

**为什么必须**：`Sprite-Lit` 材质的颜色计算依赖场景中的光照结果。如果没有 Light2D，光照贡献为 0，乘出来的颜色就是黑色。`Sprite-Unlit` 则跳过光照计算。

**面试可以这么表述**：「把材质换成了 Sprite-Lit 就必须提供光源，这是渲染管线的设计而不是 Unity 的 bug。要么加全局 Light2D，要么把不改光照的对象换回 Unlit 材质。」——能说清「为什么」比知道「怎么修」更有价值。

**其他 URP 常识**

- Renderer Feature：往管线里插自定义 pass（描边、全屏后处理）
- Volume：后处理（Bloom、色差、暗角）通过 Volume 配置
- Renderer Data：把不同光照方案分成不同 Renderer，按需切换

## 2.17 渲染基础：DrawCall、合批、图集、SRP Batcher

**结论**：DrawCall 是「让 GPU 画一次的指令」。次数越多，CPU 提交开销越大。2D 游戏的目标通常是把 DrawCall 压到几十以内（而不是几百）。

**核心概念**

| 概念 | 含义 |
| --- | --- |
| DrawCall | 一次绘制调用，CPU 侧有固定开销 |
| Batch | 把多个物体合并成一次绘制 |
| Overdraw | 同一像素被画多次（透明物体叠加的常见问题） |
| SetPass | 切换材质/着色器状态，比 DrawCall 更贵 |

**合批的三种**

1. **Static Batching**（静态合批）：把不动的物体合并，构建时烘焙。
2. **Dynamic Batching**（动态合批）：运行期合并小网格，受顶点数限制。
3. **SRP Batcher**（URP 下）：把「同 Shader 不同材质」的常量缓冲区合并提交，**效果好且不需要物体静止**。

**Sprite Atlas（图集）是 2D 项目的头号手段**

- 把多张小图打进一张大图，这样它们**共用同一个纹理**，可以被合批成一次 DrawCall。
- 没有图集：每个 sprite 用自己的纹理 → 每张都是一次 DrawCall
- 有图集：同一图集里的 sprite 可以合批

**怎么验证**：`Window → Analysis → Frame Debugger`，逐 DrawCall 看一帧的绘制顺序，以及每次「为什么合批失败」。这是面试里被问「你怎么优化的」时的标准操作。

**你项目里的现状**：纯色方块 + `PrimitiveSprite.White`，所有 sprite 共用一张纹理，**合批条件天然满足**。这是一个可以主动说出来的设计取舍：「原型期用统一白色方块，除了不依赖美术资源，还顺便保证了合批条件——后续接入真实美术时再按图集组织。」

**Sprite 的额外开销点**

- `SpriteRenderer.color` 改变会触发材质属性替换，破坏 SRP Batcher（应改用 MaterialPropertyBlock）
- 每个 SpriteRenderer 有独立的 `sortingOrder` 时可能打乱合批顺序

> 这一部分的答案全都能从你自己的代码里长出来——这是你最该提前准备的部分，

## 3.1 状态机

**结论**：状态机 = 「当前处于什么状态」+「这个状态每帧做什么」+「什么条件下切换到哪个状态」。它把一团 if-else 变成一张可读的表。

**你项目里的实现（enum + switch）**

```csharp
public enum PlayerState { Free, Attack, Dodge, Hurt, Stun, Dead }

void FixedUpdate()
{
    _stateFrame++;
    switch (State)
    {
        case PlayerState.Free:   TickFree();   break;
        case PlayerState.Attack: TickAttack(); break;
        case PlayerState.Dodge:  TickDodge();  break;
        case PlayerState.Hurt:   TickHurt();   break;
        case PlayerState.Stun:   TickStun();   break;
    }
}
```

**这个实现好在哪（说清楚才算懂）**

- 每个状态一个 `Tick` 方法：读代码时不用在几百行里找分支
- `_stateFrame` 统一递增：所有状态的持续时间都用帧计数，语言一致
- 进入状态时重置 `_stateFrame = 0`：这是「状态机正确性」的关键，漏了就会让新状态带着旧状态的计时
- 死亡状态不进入 `switch`：`if (State != PlayerState.Dead)` 单独挡掉

**这种写法的代价**

- 状态一多，`PlayerCombat` 会膨胀（现在 453 行，已经接近上限）
- 状态之间的切换逻辑散落在各个 `Tick` 里，要理清「谁能进谁」得通读全文
- 无法按状态挂载不同的数据（比如每个状态自己的参数）

**状态模式（进阶做法）**

```csharp
public abstract class PlayerStateBase
{
    public abstract void Enter(PlayerCombat ctx);
    public abstract void Tick(PlayerCombat ctx);
    public abstract void Exit(PlayerCombat ctx);
}

public class AttackState : PlayerStateBase { ... }
public class DodgeState  : PlayerStateBase { ... }
```

好处：每个状态一个文件、状态自己的数据自己管、状态切换集中管理。
代价：对象/类数量增加，简单项目反而变重。

**面试的正确回答方式**：不要说「应该用状态模式」。要说：

> 「我原型期用 enum + switch，因为状态只有 6 个，读起来最直观。当状态数超过 10 个、或者每个状态需要自己的数据和子状态时，我会迁移到状态模式——好处是每个状态独立成类，坏处是引入更多对象。**具体用哪个取决于状态的数量和状态之间共享数据的程度。**」

这句话体现的是判断力，不是背诵。

## 3.2 分层状态机与行为树

**结论**：当单一状态机表达不了「角色同时在战斗状态和移动状态」时，需要分层；当 AI 的决策逻辑复杂到无法用状态之间的转移描述时，用行为树。

| 方案 | 适合什么 | 典型场景 |
| --- | --- | --- |
| 扁平状态机 | 状态少、互斥、转移清晰 | 玩家角色（你的实现） |
| 分层状态机 | 有「叠加」语义 | 上层=战斗/非战斗，下层=移动/待机 |
| 行为树 | 决策树深、需要复用子树、需要可配置 | NPC、Boss AI、复杂单位的技能选择 |

**你项目里其实已经有一个「微型的权重选择 + 连招序列」，它介于状态机和行为树之间**

```csharp
// Scripts/Enemy/BossController.cs
int chosen = ChoosePattern(distance);   // 按距离过滤 + 权重随机（决策）
StartPattern(chosen);                   // 执行一连串步骤（序列节点）
```

`ChoosePattern` 本质是「选择节点（Selector）」：按 `minRange` / `maxRange` 过滤候选，按 `weight` 加权随机。
`BossPattern.steps` 本质是「序列节点（Sequence）」：一步步跑完，每步之间有 `stepGapFrames` 间隔。

**面试时可以这么讲**：「我的 Boss 用的是『手写的轻量行为树』——选择节点是加权随机 + 距离过滤，序列节点是连招步骤列表。之所以不引入完整的行为树框架，是因为现在只有三个招式，手写更可控。如果招式数到十几个、或者需要跨角色复用子树，我会换成数据驱动的行为树。」

**行为树的四个基本节点（知道即可）**

- Sequence：全部子节点成功才成功（先 A 再 B 再 C）
- Selector：有一个成功就成功（优先 A，不行就 B，再不行 C）
- Decorator：修饰子节点（直到成功、取反、冷却）
- Leaf：实际动作（移动、攻击、等待）

## 3.3 数据驱动设计

**结论**：把「数值和结构」从代码里抽出来放进数据（表 / SO / JSON），代码只负责解释数据。改数值不用改代码、不用重新编译，还能让非程序员参与。

**你项目里的三层数据驱动（这是一个很好的回答框架）**

| 层 | 你项目里的载体 | 驱动了什么 |
| --- | --- | --- |
| 招式帧数据 | `AttackProfile`（前摇/判定/后摇/判定盒/可格挡） | 一次攻击的全部行为 |
| 全局数值 | `CombatTuning`（ScriptableObject） | 所有角色、所有系统 |
| 动作序列 | `BossPattern.steps[]` | Boss 的连招编排 |

**为什么这套设计值钱**

```csharp
// 加一个新招式：只需要在 CombatTuning 的列表里加一条
// 加一个新的 Boss 连招：只需要在 bossPatterns 里加一个 BossPattern
// 完全不需要改 AttackRunner / DamageResolver / Hitbox
```

**这就是「对扩展开放、对修改关闭」（开闭原则）的具体体现。** 面试时说这句，再补一句你项目里的一手证据，效果远好于空谈原则。

**数据驱动的边界（能说出边界才是真懂）**

- 数据驱动适合「结构相同、参数不同」的东西。
- 一旦需要「不同的行为逻辑」（比如一个新招式要在判定期间召唤小怪），纯数据就表达不了，得加「行为字段 + 枚举分支」或「脚本绑定」。那时纯数据方案会开始变复杂——**这就是为什么很多项目最后会把「配置表」和「代码」混用**。

**再进一步的方向（任务 A8）**：把 `AttackProfile` 从内嵌在 SO 里改成外部的 CSV / JSON 配置表，写一个导入工具生成 SO。这样数值可以交给 Excel 编辑、可以 diff、可以批量校验。

## 3.4 观察者模式（事件）

**结论**：观察者模式 = 「我不认识你，但你出事的时候我会收到通知」。发布者只管发，订阅者只管收，双方不知道对方是谁。

**你项目里的实现**

```csharp
// 发布者：Health 只在数值变化时广播，不关心谁在听
public event Action<float, float> Changed;   // (当前血量, 最大血量)
public event Action<float> Damaged;
public event Action Died;

// 订阅者：HUD 只订阅，不认识 Health 的具体逻辑
health.Changed += OnHealthChanged;
```

**这套设计解决了什么**

- `Health` 不知道 HUD 存在 → 删掉 HUD 不影响战斗
- `Health` 不知道 `PlayerCombat` 存在 → 换成别的角色控制器也能用
- 一个事件可以有多个订阅者（HUD + 特效 + 音效 + 成就系统）

**你项目里的事件地图（面试时可以手画出来）**

| 发布者 | 事件 | 谁在用 |
| --- | --- | --- |
| `Health` | `Changed` / `Damaged` / `Died` | HUD、`PlayerCombat`、`BossController` |
| `Stamina` | `Changed` | HUD 体力条 |
| `Stagger` | `Changed` / `Broken` / `Recovered` | HUD 韧性条、`BossController` |
| `Hitbox` | `HitLanded` | `AttackRunner` |
| `AttackRunner` | `PhaseChanged` / `Finished` / `Landed` | `PlayerCombat` / `BossController` |

**事件的代价（要说出来）**

- 阅读代码时的「跳转地狱」：光看调用处不知道谁会响应
- 调试困难：事件是隐式的，断点不好下
- 订阅泄漏（见 1.5）

**所以**：事件适合「一对多、跨越模块边界」的通知，不适合「一对一的顺序调用」——后者直接调方法更清楚。你项目里 `DamageResolver` 直接调 `guard.EvaluateBlock(...)` 而不发事件，就是正确的判断。

## 3.5 命令模式与输入缓冲

**结论**：把「玩家的意图」封装成一个对象（命令），存进队列延后或按时消费。动作游戏的**输入缓冲**就是它的应用。

**你项目里的实现**

```csharp
// Scripts/Player/PlayerInputReader.cs
if (Input.ConsumeAttack()) { StartAttack(1); return; }
if (Input.ConsumeDodge())  { TryDodge(); }
```

`ConsumeXxx()` 的语义是「如果这个输入被缓冲了，就取走并清空」——**一次输入只能被消费一次**，这就是命令队列的核心语义。

**为什么动作游戏必须有输入缓冲**

玩家在**后摇期间**提前按了攻击键。如果没有缓冲：

- 那一帧角色还在后摇，不接受输入 → 这次按键被丢弃
- 玩家感到「我明明按了却没反应」→ 手感很差

有缓冲（`comboBufferFrames = 8`）：按键被存下来，后摇结束的那一帧再消费 → 「我按了就一定会出招」。

```csharp
// PlayerCombat.TickAttack()
if (Runner.Phase == AttackPhase.Recovery)   // 后摇 = 取消窗口
{
    if (_comboIndex < 3 && Input.ConsumeAttack()) { StartAttack(_comboIndex + 1); return; }
    if (Input.ConsumeDodge()) { TryDodge(); }
}
```

这里还体现了**取消窗口（cancel window）**的设计：后摇期间可以接下一段连招，或者闪避取消。这是动作游戏「流畅感」的关键机制，也是「后摇」存在的意义——**没有后摇就没有攻防节奏**。

**面试可以这么讲**：把「输入缓冲」「取消窗口」「前摇可被读、后摇是惩罚」这三件事一起讲，再说明它们都由 `CombatTuning` 里的帧数参数控制。这是完整的动作游戏框架理解。

## 3.6 单例

**结论**：单例保证「全局只有一个实例 + 提供一个全局访问点」。它方便，但也是耦合的来源，要限用。

**你项目里有两种单例写法，正好可以对比**

```csharp
// 写法一：Awake 里注册，场景内单例（HitStopManager）
void Awake()
{
    if (Instance != null && Instance != this) { Destroy(gameObject); return; }
    Instance = this;
}
void OnDestroy() { if (Instance == this) Instance = null; }

// 写法二：访问时按需创建，常驻单例（UIManager）
public static UIManager Instance
{
    get
    {
        if (_instance == null)
        {
            var go = new GameObject("[UIManager]");
            _instance = go.AddComponent<UIManager>();
        }
        return _instance;
    }
}
```

| | 场景内单例 | 按需创建的单例 |
| --- | --- | --- |
| 谁负责创建 | 场景里的对象 | 代码自己 |
| 生命周期 | 随场景 | 可以 `DontDestroyOnLoad` 常驻 |
| 风险 | 场景里忘了放就空引用 | 访问时机不确定，可能在错误的作用域里被创建 |
| 适合 | 场景相关的管理器 | 跨场景的全局服务（UI、音频、存档） |

**面试必答：单例的三个问题**

1. **隐式依赖**：任何代码都能访问单例，导致依赖关系看不出来，测试时无法替换。
2. **生命周期不清**：什么时候被创建、什么时候被销毁，容易出现「用着用着变 null」。
3. **关闭 Domain Reload 后 static 残留**（见 1.14）。

**替代方案**：把依赖显式注入（你的 `PlayerCombat` 用 `public Health Health` 而不是 `GetComponent`，就是在做这件事）；或者用一个 `GameContext` 对象持有所有管理器，通过参数传递。

**你项目里的亮点**：`HitStopManager.Instance?.Request(...)` 用了 `?.` 空合并——**单例为 null 时不会崩，而是静默跳过**。这是「让可选依赖真的可选」的正确写法，可以主动讲。

## 3.7 依赖注入与引用获取

**结论**：依赖注入 = 「我需要什么，你从外面给我」，而不是「我自己去找」。在 Unity 里最实用的形式是「Inspector 里拖引用」。

| 方式 | 速度 | 稳定性 | 适合 |
| --- | --- | --- | --- |
| Inspector 序列化引用 | 最快（序列化时已绑定） | 重命名/移动对象不受影响 | **首选** |
| `GetComponent<T>()` in Awake | 快（只查一次） | 结构变了会断 | 组件在同一个对象上 |
| `GetComponentInChildren<T>()` | 中（遍历子树） | 同上 | 子物体上 |
| `FindObjectOfType<T>()` | 慢（全场景遍历） | 依赖场景内容 | 只应在初始化时用一次 |
| `GameObject.Find("名字")` | 慢且脆弱 | 改名字就崩 | **避免** |

**你项目里的做法**

```csharp
// 好：显式引用，Inspector 拖进去
public PlayerInputReader Input;
public PlayerMotor Motor;
public AttackRunner Runner;
public Health Health;

// 也好：只查一次并缓存
public void Resolve()
{
    if (health == null) health = GetComponentInParent<Health>();
    guard = FindInterface<IDamageGuard>();
}
```

**`Hurtbox.FindInterface<T>()` 这个手写方法值得讲**：

```csharp
T FindInterface<T>() where T : class
{
    var behaviours = GetComponentsInParent<MonoBehaviour>();
    for (int i = 0; i < behaviours.Length; i++)
        if (behaviours[i] is T found) return found;
    return null;
}
```

Unity 没有 `GetComponent<IInterface>()` 的泛型接口版本，所以只能这么找。**注意 `GetComponentsInParent` 会分配一个数组**——如果放在 `Update` 里就是每帧 GC。你的代码是在 `Awake` 里调一次，所以没问题。这个「知道它会分配、所以放在初始化里」的判断，正是面试官想听到的。

---

## 3.8 分层架构与依赖方向

**结论**：好的架构里，依赖是有方向的。上层可以依赖下层，下层不应该知道上层存在。

**你的项目其实已经有清晰的分层**

```
表现层     UI / HUD / HitSpark / CameraShake / ColorFlash
   ↑
框架层     UIManager、HitStopManager、GamePause
   ↑
规则层     DamageResolver（伤害裁决）、AttackRunner（帧流程）、BossController（决策）
   ↑
数据组件层 Health / Stamina / Stagger / Hurtbox / Hitbox
   ↑
数据       AttackProfile / CombatTuning（纯数据，不认识任何人）
```

**依赖方向的证据**

```csharp
// DamageResolver（规则层）知道 Hurtbox（数据层）—— 上层依赖下层 ✓
// Hurtbox 完全不知道 DamageResolver 存在   —— 下层不认识上层 ✓
public class Hurtbox : MonoBehaviour
{
    public Health health;
    public Stagger stagger;
    // 没有任何对 DamageResolver 的引用
}
```

**为什么这么设计重要**

- `Hitbox` 里只需要 `DamageResolver.Resolve(ref info, target)` 一行，规则怎么改都不用碰判定代码
- `Hurtbox` 可以被任何角色复用（玩家、Boss、小怪），因为它们只需要提供 `Health` / `Stagger`
- 想加新角色：写好数据组件 + 一个能 `IDamageGuard` 的控制器即可，规则层零改动

**面试时的杀手锏**：当场画出这张分层图，然后说「加一个新 Boss，我需要改的只有 `CombatTuning` 里的数据和 `BossController` 的决策，`DamageResolver`、`Hitbox`、`Hurtbox` 一行都不用动。」——**具体的可扩展性承诺，比背诵 SOLID 原则强十倍。**

**一个可以主动承认的不足**：`BossController` 目前既做决策（选哪招）又做执行（跑连招），职责偏重。如果要严谨分层，可以把「决策」抽成一个 `IBossBrain`，`BossController` 只负责执行。**能指出自己架构的不足，是成熟的信号。**

## 3.9 帧同步与状态同步

**结论**：帧同步传「输入」，状态同步传「状态」。动作游戏和 RTS 多用帧同步，MMO 和回合制多用状态同步。

| | 帧同步（Lockstep） | 状态同步 |
| --- | --- | --- |
| 网络上传什么 | 玩家的**输入指令** | 服务器算完的**状态** |
| 谁在算 | 每个客户端各自算 | 服务器算 |
| 带宽 | 很小（只传输入） | 大（要传状态） |
| 一致性要求 | **必须确定性** | 服务器是权威 |
| 断线重连 | 要回放全部输入 | 直接同步当前状态 |
| 作弊难度 | 低（客户端全知） | 高 |
| 典型游戏 | 星际争霸、王者荣耀、格斗游戏 | MMO、棋牌、回合制 |

**为什么帧同步要求确定性（和你项目相关）**

- 所有客户端必须算出**完全相同**的结果，否则会「不同步」
- 所以：不能用 `float` 的随机数（要用定点的确定性随机）、不能用 `Time.deltaTime`（帧率不同）、遍历顺序必须稳定
- **这就是你用帧计数而不是时间累加的意义**——虽然你现在是单机，但这个习惯让你天然理解帧同步的前提

**面试可以这么回答**：「我的项目是单机，但我在设计时用了帧数据驱动和确定性逻辑，这让我能理解帧同步的前提条件。具体来说，帧同步里最怕的是浮点误差累积和不确定的遍历顺序——比如用 `Dictionary` 的遍历顺序在帧同步逻辑里就是危险的，因为不同运行时的哈希实现可能不同。」

**这个回答的价值**：它把「你的单机项目」和「网络游戏的技术要求」连接起来了，展现的是可迁移的理解，而不是背一条定义。

# 第四部分 · 性能优化

## 4.1 Profiler 全模块

**结论**：Profiler 是性能问题的唯一入口。**没有数据就不要谈优化**——这是面试官判断你有没有真做过优化的第一条标准。

| 模块 | 看什么 |
| --- | --- |
| CPU Usage | 每帧各函数耗时、`GC Alloc` 列、调用栈 |
| GPU Usage | 各渲染阶段的耗时 |
| Rendering | DrawCall、SetPass、三角形数、批次 |
| Memory | 托管堆、纹理、网格、音频各占多少 |
| 其他 | Physics、Audio、UI、Global Illumination 等专项 |

**关键操作**

- 点击 `GC Alloc` 列排序 → 立刻找到最大的分配来源
- 双击某一行 → 展开调用栈，看到具体是哪个方法分配的
- `Deep Profile` 更细但会显著拖慢运行，只用于精确定位
- `Record` 一段时间再停止，看整体趋势而不是单帧

**验收标准**：能指着 Profiler 说「这个函数每帧分配 2KB，来自这里的字符串拼接」，而不是「我感觉有点卡」。

---

## 4.2 GC Alloc 定位与消除

**结论**：游戏卡顿的常见原因不是「帧太慢」，而是「GC 突然触发」。目标是把稳定状态的 GC Alloc 压到接近 0。

**定位流程**

1. Profiler → CPU → 运行一段典型战斗（连续攻击 + 受击 + 特效）
2. 按 `GC Alloc` 排序
3. 找项目自己的代码（Unity 内部的分配通常无法消除），记录下来
4. 逐个修（对象池 / 缓存 / 去掉闭包 / 去掉 LINQ / 改字符串处理）
5. 重测，记录 `GC Alloc` 变化

**你项目的三个待修点**

| 位置 | 问题 | 修法 |
| --- | --- | --- |
| `HitSpark.Spawn` | 每次命中 new GameObject + AddComponent + Destroy | 对象池（任务 A2） |
| `Hitbox.FixedUpdate` | `OverlapBoxAll` 每次返回新数组 | 预分配 List + `OverlapBox` 重载（任务 A3） |
| `Hitbox` 每帧 `GetComponentInParent<Hurtbox>()` | 重复查找 | `Dictionary<Collider2D, Hurtbox>` 缓存 |

**验收数据（写进简历的那句）**：优化前 `___ KB/帧` → 优化后 `0 KB/帧`。**必须有截图。**

---

## 4.3 DrawCall 优化

**结论**：DrawCall 是 CPU 侧开销，2D 游戏要把数量压下来，主要靠**图集**和**合批**。

**排查顺序**

1. Game 视图右上角 Stats 面板先看个大概（DrawCall / Batches / Tris）
2. `Window → Analysis → Frame Debugger` 逐条看
3. 找「为什么这次没合批」——常见原因：纹理不同、材质不同、中间插了别的物体打乱顺序、被 UI 打断
4. 修：打进同一张 Sprite Atlas、统一材质、调整 `sortingOrder` 让同图集的相邻

**2D 项目的高频问题**

- 每个 sprite 一张独立贴图 → 每张一个 DrawCall
- UI 和场景物件交替渲染 → 打断合批
- 半透明物体重叠 → Overdraw，GPU 侧压力

**你项目的现状**：全部使用 `PrimitiveSprite.White` 同一张纹理，天然合批。**这是一个可以主动讲的取舍**：原型期统一白色方块，除了不依赖美术资源，也顺便保证了合批条件；后续接入真实美术时，会按图集（图对象、图特效、图 UI）组织。

---

## 4.4 内存优化

**结论**：内存优化关注三件事——**纹理**（通常最大头）、**托管堆**（GC 压力）、**资源冗余**（同一资源多份实例）。

| 方向 | 手段 |
| --- | --- |
| 纹理 | 按用途选压缩格式；尺寸不超过实际显示大小的 2 倍；2D 精灵图集化 |
| 音频 | 短音效用 Decompress On Load；长音乐用 Streaming |
| 网格 | 减少顶点数；不需要读写时关闭 Read/Write |
| 托管堆 | 消除每帧分配；避免大数组反复创建 |
| 资源 | 及时 `Release` / `UnloadUnusedAssets`；避免重复加载同一资源 |
| 对象池 | 上限要设置，否则只增不减 |

**面试常问**：「你怎么判断内存问题？」→ Memory Profiler 里看「Take Snapshot」的两次对比，看哪个类别增长了。**能说出「两次快照对比找增长点」就是加分。**

---

## 4.5 优化闭环（怎么把优化讲成故事）

**结论**：优化不是「做了几件事」，而是「测量 → 定位 → 修改 → 复测」的闭环。面试官要的是这个闭环，不是一堆零散技巧。

**讲故事的模板**

> 「我做了一次战斗性能优化。首先在 Profiler 里跑一段典型战斗，发现每帧 `GC Alloc` 有大约 ___ KB，主要来自两处：命中特效每次 `new GameObject`，以及 `Hitbox` 每帧用 `OverlapBoxAll` 返回新数组。
> 针对第一处我引入了 `UnityEngine.Pool.ObjectPool` 池化特效对象，并在 `OnEnable` 里统一重置状态；针对第二处我改成用预分配的 `List<Collider2D>` 接收查询结果，并把 `Hurtbox` 查找结果缓存进字典。
> 复测后战斗帧的 `GC Alloc` 降到 0，连续命中 100 次不再触发 GC。DrawCall 方面，因为原型期统一使用同一张纹理，合批本来就没有问题，但我在 Frame Debugger 里验证了一遍。」

**这个回答里的关键词**：Profiler 定位、具体数字、具体手段、复测验证。**没有「我觉得变快了」，这是关键。**

# 第五部分 · 数学基础

## 5.1 向量运算

**结论**：三个操作覆盖了动作游戏 90% 的向量需求——点积判夹角、叉积判左右、归一化求方向。

```csharp
// 1. 方向（求单位向量）
Vector2 dir = (target - self).normalized;

// 2. 距离
float dist = Vector2.Distance(a, b);        // 内部是 (a-b).magnitude
float sqr  = (a - b).sqrMagnitude;          // 只需要比较远近时用它，省一次开方

// 3. 点积：判断同向/垂直/反向，也用来算夹角
float dot = Vector2.Dot(forward, toTarget); // >0 在前方，=0 垂直，<0 在后方
float angle = Mathf.Acos(dot) * Mathf.Rad2Deg;

// 4. 叉积（2D 里返回 z 分量，是标量）
float cross = forward.x * toTarget.y - forward.y * toTarget.x;
// cross > 0 = 目标在左侧，< 0 = 右侧
```

**实用技巧：`sqrMagnitude` 代替 `magnitude`**。开方是相对昂贵的运算，如果只是比较「谁更近」，比较平方距离即可。

```csharp
// 差
if (Vector2.Distance(a, b) < 5f) ...
// 好
if ((a - b).sqrMagnitude < 25f) ...
```

**你项目里的例子**

```csharp
// Scripts/Player/PlayerCombat.cs —— 判断攻击者在哪一侧（叉积的简化版）
float directionToAttacker = Mathf.Sign(info.attacker.position.x - transform.position.x);
if (!Mathf.Approximately(directionToAttacker, Motor.Facing)) return BlockOutcome.NotBlocked;
```

这是「只能挡正面」的实现。注意它用了 `Mathf.Approximately` 而不是 `==`——浮点比较必须用近似判断，正是你自检清单里的那条。

## 5.2 插值家族

**结论**：四个插值函数，语义完全不同，混用会造成「速度不一致」或「永远到不了」的问题。

| 函数 | 语义 | 典型用途 |
| --- | --- | --- |
| `Mathf.Lerp(a, b, t)` | 线性插值，`t` 是 0~1 的比例 | 已知比例的混合 |
| `Vector2.Lerp(a, b, t)` | 同上，按分量 | 位置混合 |
| `Mathf.MoveTowards(cur, target, maxDelta)` | 以固定速度靠近，**不会超调** | 匀速移动到目标 |
| `Vector3.SmoothDamp(...)` | 带缓动的平滑逼近 | 相机跟随 |
| `Vector2.Slerp(a, b, t)` | 球面插值，保持长度 | 方向/旋转混合 |

**最大的坑：`Lerp` 当阻尼用**

```csharp
// 差：永远到不了目标，而且速度随帧率变化
transform.position = Vector2.Lerp(transform.position, target, 0.1f);

// 好：用 deltaTime 修正
transform.position = Vector2.Lerp(transform.position, target, 1f - Mathf.Exp(-10f * Time.deltaTime));

// 或者直接用 SmoothDamp（推荐）
transform.position = Vector3.SmoothDamp(transform.position, target, ref _velocity, 0.2f);
```

`Lerp(cur, target, 0.1f)` 每次只走剩余距离的 10%，**距离越近走得越慢，理论上永远到不了**；而且 60fps 比 30fps 快一倍。

**你项目里的例子**

```csharp
// Scripts/Combat/Hitbox.cs —— 命中点取两盒中心的中间
Vector2 hitPoint = new Vector2(
    Mathf.Lerp(center.x, target.Center.x, 0.5f),
    Mathf.Lerp(center.y, target.Center.y, 0.5f));
```

这里的 `t = 0.5f` 是固定的，语义是「取中点」而不是「阻尼」，所以完全正确——**同一函数，语义不同，这是能讲出来的细节。**

**相机跟随为什么放 `LateUpdate`**：因为要在所有角色的 `Update` 走完之后再算相机位置，否则相机会比角色慢一帧，画面抖动。

## 5.3 三角函数与角度

**结论**：`sin` / `cos` 用于圆周运动与极坐标；`atan2` 用于从向量反推角度。

| 函数 | 用途 |
| --- | --- |
| `Mathf.Sin(rad)` / `Mathf.Cos(rad)` | 圆周运动、波形（呼吸动画、浮动） |
| `Mathf.Atan2(y, x)` | 从向量得到角度（**推荐，比 `Atan` 更好用**） |
| `Mathf.Rad2Deg` / `Deg2Rad` | 弧度与角度互转 |
| `Mathf.Repeat` | 循环取模（做滚动纹理） |
| `Mathf.PingPong` | 往返（做往复动画） |

```csharp
// 圆周运动
float x = center.x + radius * Mathf.Cos(angle);
float y = center.y + radius * Mathf.Sin(angle);

// 朝向目标的角度（2D 常用）
Vector2 dir = target - transform.position;
float degrees = Mathf.Atan2(dir.y, dir.x) * Mathf.Rad2Deg;
```

**为什么用 `Atan2(y, x)` 而不是 `Atan(y/x)`**：`Atan` 丢失象限信息（第一象限和第三象限结果相同），`Atan2` 用两个参数保留了正负号，能正确区分四个象限。这是很常见的面试细节题。

## 5.4 2D 物理概念

**结论**：动作游戏里的「手感」本质上就是一组物理参数的组合。理解它们，才能有目的地调，而不是碰运气。

| 概念 | 在 Unity 里的对应 | 手感影响 |
| --- | --- | --- |
| 速度 | `Rigidbody2D.velocity` | 移动快慢 |
| 加速度 | 每帧给 velocity 加值 | 起步/刹车的重量感 |
| 重力 | `gravityScale` + 项目重力 | 跳跃高度、下落速度 |
| 重力缩放 | `gravityScale` | 你项目设 3.6，加大下落感 |
| 摩擦/阻力 | `Linear Drag` | 松手后滑多远 |
| 弹性 | `Physics Material 2D` 的 bounciness | 落地弹跳 |
| 冲量 | `AddForce(force, ForceMode2D.Impulse)` | 击退、跳跃起跳 |

**跳跃手感的四个标准参数（你项目里都有了）**

```csharp
public int   coyoteFrames = 6;          // 土狼时间：离开平台后仍能起跳
public int   jumpBufferFrames = 6;      // 跳跃缓冲：落地前按跳，落地瞬间自动起跳
[Range(0,1)] public float jumpCutMultiplier = 0.45f;  // 松手截断：短按小跳
public float gravityScale = 3.6f;       // 下落比上升快
```

**这套组合被称为「现代平台跳跃四件套」**，面试时能说出这四点，说明你不是只会写 `velocity.y = jumpForce`。

**你项目里更聪明的一点**：跳跃参数的**判定**交给 `PlayerMotor`（它有 `TickInput`、`QueueJump`、`CancelJumpQueue`），`PlayerCombat` 只负责「要不要跳」。这是「手感逻辑集中在一处」的正确做法——将来调跳跃手感只改 `PlayerMotor`，不碰状态机。

## 5.5 圆形与矩形的相交判定

**结论**：`Physics2D.OverlapBox` 背后是 AABB（轴对齐包围盒）测试。理解原理，才能在面试里解释「为什么这么写」。

**AABB 相交判定（两个轴分别判断）**

```csharp
// 两个矩形相交的充要条件：在 x 轴和 y 轴上的投影都重叠
bool Overlaps(Rect a, Rect b)
{
    return a.xMin < b.xMax && a.xMax > b.xMin &&
           a.yMin < b.yMax && a.yMax > b.yMin;
}
```

**圆与矩形**

```csharp
// 把圆心钳制到矩形范围内，得到矩形上离圆心最近的点，再比较距离
Vector2 closest = new Vector2(
    Mathf.Clamp(circle.x, rect.xMin, rect.xMax),
    Mathf.Clamp(circle.y, rect.yMin, rect.yMax));
bool hit = (closest - circle).sqrMagnitude <= radius * radius;
```

**你的判定盒不是 AABB，而是「有朝向的矩形」**

```csharp
// Hitbox.BoxCenter
Vector2 center = new Vector2(
    origin.x + _profile.boxOffsetX * facing,   // 按朝向翻转偏移
    origin.y + _profile.boxOffsetY);
```

攻击盒本身仍是轴对齐矩形，只是**偏移量按朝向镜像**。这是 2D 动作游戏最常见的做法：省掉了旋转矩形的判定复杂度，同时攻击范围能跟着朝向走。

**面试延伸**：如果被问「角色斜着举剑怎么办」→ 用旋转矩形（OBB）判定，或者用多边形 `PolygonCollider2D` + `OverlapPolygon`。代价是判定复杂度上升，且需要额外的可视化调试工具。**你项目现在不需要，但你要知道这条路存在。**

## 6.1 复杂度分析

**结论**：面试第一句永远是「这个解法的时间/空间复杂度是多少」。答不上来，方案再对也扣分。

| 复杂度 | 名称 | n=1000 时的量级 |
| --- | --- | --- |
| O(1) | 常数 | 1 |
| O(log n) | 对数 | 10 |
| O(n) | 线性 | 1000 |
| O(n log n) | 线性对数 | 10000 |
| O(n²) | 平方 | 1,000,000 |

**要点**：只保留最高阶项、忽略常数系数；空间复杂度算的是**额外**空间（不把输入算进去）；递归要考虑调用栈深度。

**练习**：写完后对每一道题说出复杂度。这个习惯本身就能在面试里加分。

## 6.3 哈希表

**结论**：遇到「找重复」「找配对」「计数」先想哈希表，用 O(n) 空间换 O(1) 查找。

| 场景 | 做法 |
| --- | --- |
| 两数之和 | 一遍遍历，检查 `target - x` 是否在表里 |
| 字母异位词 | 排序后作 key，或字符计数作 key |
| 最长连续序列 | 全部放 `HashSet`，只从「没有前驱」的数开始数 |
| 前 K 个高频元素 | 哈希计数 + 小顶堆 |

```csharp
// 两数之和的标准写法
public int[] TwoSum(int[] nums, int target)
{
    var map = new Dictionary<int, int>();      // 值 → 下标
    for (int i = 0; i < nums.Length; i++)
    {
        int need = target - nums[i];
        if (map.TryGetValue(need, out int j)) return new[] { j, i };
        map[nums[i]] = i;
    }
    return Array.Empty<int>();
}
```

**面试注意**：这里 `TryGetValue` 只查一次——和 1.9 讲的是同一件事，**C# 的 `Dictionary` 用法和算法题是同一个知识点**。

## 6.4 链表

**核心技巧**：虚拟头节点（dummy head）、快慢指针。

| 题 | 技巧 |
| --- | --- |
| 反转链表 | 三指针迭代（prev / cur / next） |
| 检测环 | 快慢指针，相遇则说明有环 |
| 合并两个有序链表 | 虚拟头节点 + 双指针 |
| 删除倒数第 n 个 | 快指针先走 n 步，再一起走 |

```csharp
// 反转链表（写不出来直接挂）
public ListNode ReverseList(ListNode head)
{
    ListNode prev = null, cur = head;
    while (cur != null)
    {
        var next = cur.next;
        cur.next = prev;
        prev = cur;
        cur = next;
    }
    return prev;
}
```

**虚拟头节点的作用**：当操作可能改变头节点时（删除、插入），加一个假节点放在头前面，代码就不用分「删的是不是头」两种情况。

## 6.5 栈与队列

| 题 | 技巧 |
| --- | --- |
| 有效括号 | 遇左括号入栈，遇右括号比对栈顶 |
| 每日温度 | 单调栈（栈里存下标，保持递减） |
| 用栈实现队列 | 两个栈，一个进一个出 |
| 滑动窗口最大值 | 单调双端队列 |

**单调栈的核心思想**：栈里始终保持单调性，新元素入栈前把「不如它的」弹掉。用来找「左边/右边第一个更大/更小的元素」。

```csharp
// 每日温度
var stack = new Stack<int>();          // 存下标
var answer = new int[temperatures.Length];
for (int i = 0; i < temperatures.Length; i++)
{
    while (stack.Count > 0 && temperatures[i] > temperatures[stack.Peek()])
    {
        int idx = stack.Pop();
        answer[idx] = i - idx;
    }
    stack.Push(i);
}
```

**注意**：`stack.Pop()` 有返回值，但直接写在索引里（`answer[stack.Pop()] = ...`）就拿不到那个下标做减法了。**先存到变量再计算**——这类「值被消费掉了」的写法错误在面试里很常见，练到能一眼看出来比背模板重要。

## 6.6 二叉树

**必须能默写的三种递归遍历 + 层序**

```csharp
void PreOrder(TreeNode n) { if (n == null) return; Visit(n); PreOrder(n.left); PreOrder(n.right); }   // 中左右
void InOrder (TreeNode n) { if (n == null) return; InOrder(n.left); Visit(n); InOrder(n.right); }      // 左中右
void PostOrder(TreeNode n){ if (n == null) return; PostOrder(n.left); PostOrder(n.right); Visit(n); }  // 左右中

// 层序（BFS）
var queue = new Queue<TreeNode>();
queue.Enqueue(root);
while (queue.Count > 0)
{
    int size = queue.Count;              // 关键：先固定本层数量
    for (int i = 0; i < size; i++)
    {
        var node = queue.Dequeue();
        if (node.left  != null) queue.Enqueue(node.left);
        if (node.right != null) queue.Enqueue(node.right);
    }
}
```

**高频题**：最大深度、对称二叉树、最近公共祖先、验证二叉搜索树、路径总和。

**`size = queue.Count` 这一句是层序遍历的灵魂**——不先固定，就分不清哪一层是哪一层。

## 6.7 排序与二分

**手写快排**

```csharp
void QuickSort(int[] a, int lo, int hi)
{
    if (lo >= hi) return;
    int pivot = a[(lo + hi) / 2], i = lo, j = hi;
    while (i <= j)
    {
        while (a[i] < pivot) i++;
        while (a[j] > pivot) j--;
        if (i <= j) { (a[i], a[j]) = (a[j], a[i]); i++; j--; }
    }
    QuickSort(a, lo, j);
    QuickSort(a, i, hi);
}
```

平均 O(n log n)，最坏 O(n²)（已排序 + 固定取首元素）。稳定排序要讲归并排序。

**二分查找的三种模板（重点是边界）**

```csharp
// 找目标值
int lo = 0, hi = nums.Length - 1;
while (lo <= hi)
{
    int mid = lo + (hi - lo) / 2;     // 防止 (lo+hi) 溢出
    if (nums[mid] == target) return mid;
    if (nums[mid] < target) lo = mid + 1;
    else hi = mid - 1;
}
```

**面试常问**：`mid = lo + (hi - lo) / 2` 为什么不写 `(lo + hi) / 2`？→ 防止整数溢出（C# 里 `int` 相加可能溢出为负）。这个细节答出来就是加分。

## 6.8 DFS / BFS

**结论**：DFS 用递归（或栈），BFS 用队列。求「最短路径/最少步数」用 BFS，求「所有方案/连通性」用 DFS。

```csharp
// 岛屿数量的 DFS 骨架
void Dfs(char[][] grid, int r, int c)
{
    if (r < 0 || r >= grid.Length || c < 0 || c >= grid[0].Length) return;  // 越界
    if (grid[r][c] != '1') return;                                         // 已访问或不是陆地
    grid[r][c] = '0';                                                      // 标记已访问
    Dfs(grid, r + 1, c); Dfs(grid, r - 1, c);
    Dfs(grid, r, c + 1); Dfs(grid, r, c - 1);
}
```

**为什么 BFS 能求最短路径**：BFS 按层扩展，第一次到达目标时经过的层数就是最少步数。DFS 不保证。

**和游戏的联系**：格子地图寻路用 BFS / A*；状态空间搜索（比如解谜关卡）也是同一套。**面试时如果能把它和游戏结合起来讲，很加分。**

## 6.9 动态规划

**结论**：DP = 「把大问题拆成重叠的子问题，记住子问题的答案」。三步走：定义状态 → 找转移方程 → 确定初始值和遍历顺序。

```csharp
// 爬楼梯：dp[i] = dp[i-1] + dp[i-2]
public int ClimbStairs(int n)
{
    if (n <= 2) return n;
    int a = 1, b = 2;                      // 滚动变量，空间 O(1)
    for (int i = 3; i <= n; i++) { int c = a + b; a = b; b = c; }
    return b;
}
```

| 题型 | 状态定义 | 代表题 |
| --- | --- | --- |
| 线性 | `dp[i]` = 前 i 个的最优解 | 爬楼梯、打家劫舍、最大子数组和 |
| 序列 | `dp[i]` = 以 i 结尾的最长/最短 | 最长递增子序列、最长公共子序列 |
| 背包 | `dp[j]` = 容量 j 时的最优值 | 零钱兑换、01 背包、完全背包 |
| 区间 | `dp[i][j]` = 区间 i~j 的解 | 最长回文子串 |

**面试提示**：DP 题先说「我用 DP 做」，再说状态定义，再说转移方程，最后才写代码。**顺序反了，面试官会以为你在背题。**

## 6.10 手写训练方法

**结论**：面试考的是「在压力下手写正确代码」，和「刷题量」不完全是一回事。

**练习方法**

1. **无补全环境**：用记事本或白纸写，写完再粘进 IDE 验证
2. **先讲后写**：每道题先说思路（2 分钟），再写代码（15 分钟），最后手测边界（3 分钟）
3. **刻意练边界**：空数组、单元素、全相同、越界、溢出
4. **错题本**：写错的题记下来，一周后重做——这和你项目的《错题本.md》是同一个方法

**高频题单（优先刷这些）**：两数之和、三数之和、反转链表、环形链表、有效括号、最长无重复子串、最大子数组和、合并区间、二叉树层序遍历、岛屿数量、爬楼梯、零钱兑换、LRU 缓存、排序数组（手写快排/归并）。

**目标**：150 道，其中 50 道能在 20 分钟内一次写对。

# 第七部分 · 游戏设计素养

> 这一部分常被技术岗考生忽略。但面试官（尤其是主程或制作人）会从这些回答里判断
> 「你是会写代码，还是懂游戏」。而且你自己的企划案就是最好的素材来源。

## 7.1 核心循环

**结论**：核心循环是「玩家每 30 秒左右重复一次的动作」，是整个游戏的发动机。循环立不住，其他都白费。

**你的企划案里的三层循环（可以直接讲）**

| 层级 | 时长 | 内容 | 断裂的后果 |
| --- | --- | --- | --- |
| 战斗循环 | 秒 | 走位 → 攻击 → 命中反馈 → 躲避 → 击杀 | 打起来不爽，其余全部白费 |
| 关卡循环 | 分钟 | 进关 → 清怪 → 开宝箱 → 关底 Boss → 结算 | 关卡失去节奏，退化成刷怪 |
| 成长循环 | 小时 | 升级 / 换装 / 强化 → 挑战更难的关 | 没有变强的实感，玩家流失 |

**面试时的表达方式**：「我的判定标准是——把『行动 → 反馈』单独拿出来玩 10 分钟还觉得爽，核心循环才算立住。做不到就还没到做美术和剧情的时候。」这句话是从你的企划案原文里来的，**它体现的是「先验证最贵的假设」这种工程思维在游戏设计上的应用。**

**加分项**：能举出反例——「很多独立游戏失败不是因为内容不够，而是因为第一个 10 分钟不好玩。」

---

## 7.2 手感调参：四个参数决定 80%

**结论**：动作游戏的手感几乎完全由四个参数决定——前摇、判定、后摇、命中停顿。

```csharp
[Header("帧数（60fps 基准）")]     // ⚠️ 注意 2.4 里提到的步长偏差
public int startupFrames  = 8;      // 前摇：出招到判定生效。越长越容易被看破、被躲掉
public int activeFrames   = 4;      // 判定：能打到人的窗口
public int recoveryFrames = 14;     // 后摇：判定结束后的僵直，是攻防转换的关键
public int hitStopFrames  = 3;      // 命中停顿：打击感的最主要来源
```

**每个参数的设计意义（面试标准答案）**

| 参数 | 作用 | 调大之后 |
| --- | --- | --- |
| 前摇 | 给玩家「读招」的时间 | 更容易被躲开、被弹反；节奏变慢 |
| 判定 | 决定命中宽容度 | 更容易打中，但动作显得"粘" |
| 后摇 | 制造风险与攻防转换点 | 打空后挨打的代价更大，节奏更硬 |
| 命中停顿 | 打击感的直接来源 | 更有力量感，但过长会打断节奏 |

**你的进阶设计（这个很值钱）**：`breakWindowFrames` —— Boss 重击后留出的破绽窗口，是「风险回报」的具体实现：重招威力大，但收招长，玩家有明确的输出机会。

```csharp
// CombatTuning 里的重砸
startupFrames = 30, activeFrames = 6, recoveryFrames = 30, breakWindowFrames = 90,
```

**面试讲述示范**：「重砸这一招前摇 30 帧、收招 30 帧再加 90 帧破绽窗口，是明确设计成『高风险高回报』的。玩家学会诱招之后可以稳定输出——这是用数值制造学习曲线，而不是靠提高敌人血量。」

## 7.3 可读性设计

**结论**：动作游戏的难度应该来自「看懂了但没做到」，不应该来自「没看懂」。所有攻击必须有可读的前摇。

**你项目里的实现**

```csharp
// Scripts/Enemy/BossController.cs
static readonly Color TelegraphBlockable   = new Color(1f, 0.85f, 0.25f, 0.55f);   // 黄
static readonly Color TelegraphUnblockable = new Color(1f, 0.25f, 0.18f, 0.65f);   // 红

Flash.SetTint(Runner.Profile.blockable ? TelegraphBlockable : TelegraphUnblockable);
```

**颜色约定的设计意图**：黄色 = 可格挡可弹反，红色 = 只能闪避。玩家不需要试错就能知道该怎么应对。

```csharp
// 弹反窗口内高亮，让玩家「看得见」那个窗口
GuardVisual.color = inWindow
    ? new Color(1f, 0.85f, 0.2f, 0.95f)
    : new Color(0.4f, 0.62f, 1f, 0.45f);
```

**这是「把不可见的系统状态可视化」的经典做法。** 弹反窗口只有 8 帧（约 160ms），如果玩家看不见，学习成本会高到让人劝退。**面试时可以主动讲这个决策：把隐性机制变成显性反馈，是降低学习门槛最有效的手段之一。**

**同类设计证据**：Boss 起手第一帧才转向，之后锁死朝向——玩家可以绕背躲开。这是「给玩家可被利用的规则」，而不是「让敌人永远正对你」。

## 7.4 资源经济设计

**结论**：给玩家的每种资源都应该有取舍。没有取舍的资源等于没有资源。

**你项目里的设计**

```csharp
/// <summary>体力。闪避与格挡共用同一条资源 —— 这样玩家必须做取舍，而不是无脑滚。</summary>
public class Stamina : MonoBehaviour { ... }
```

**为什么共用一条体力是好的设计**

- 如果闪避和格挡各自独立，玩家的最优策略就是「两个都疯狂用」
- 共用一条之后，**闪避消耗的正是「能不能挡住下一刀」的资本**——每一个动作都有机会成本
- 破防机制（体力不足 → 长硬直）把这条资源的价值钉死了

```csharp
// 弹反不消耗体力，这是它比普通格挡强的地方
case BlockOutcome.Parried: Flash.Flash(ParryFlashColor, 0.16f); break;
```

**弹反的「零消耗 + 高回报」是典型的技巧奖励设计**：技术好的玩家可以获得额外资源，形成正反馈。但同时弹反窗口只有 8 帧，风险与收益匹配。

**面试讲述示范**：「我给闪避和格挡共用一条体力，这样玩家必须做取舍而不是无脑连滚。弹反窗口只有 8 帧但零消耗，所以高手的资源会越来越宽裕——这是用资源系统制造技术分层。」

## 7.5 竞品拆解

**结论**：能拆解一款成品游戏，是「懂游戏」的最直接证明。选一款你真正玩过的动作游戏，写两页足够。

**拆解模板**

```
1. 核心循环是什么？每 30 秒玩家在做什么？
2. 战斗资源有哪些（血、能量、弹药、架势条）？怎么获得、怎么消耗？
3. 敌人的可读性怎么做的（前摇、颜色、音效、动画）？
4. 难度曲线怎么设计的？什么时候给新机制？
5. 死亡惩罚是什么？为什么玩家愿意重来？
6. 如果让我改一个地方，我改什么？为什么？
```

**推荐候选（都适合 2D / 动作视角）**：空洞骑士（探索 + 战斗节奏）、只狼（弹反为核心的对刀）、Ender Lilies（2D 横版 + 手感）、茶杯头（Boss 战设计）、死亡细胞（循环与随机）。

**第 6 问是关键**：「如果让我改一个地方」这一问，是面试官判断你有没有独立判断力的地方。**不要只说优点，要给出有理由的批评。**

# 第八部分 · 工程化与协作

## 8.1 git 工作流

**结论**：git 是最基本的职业素养。作品集没有版本控制，等于没有作品集。

**Unity 项目必须的 `.gitignore` 核心条目**

```
[Ll]ibrary/
[Tt]emp/
[Oo]bj/
[Bb]uild/
[Bb]uilds/
[Ll]ogs/
[Uu]ser[Ss]ettings/
*.csproj
*.sln
*.user
*.pidb
*.booproj
.vs/
.idea/
```

**为什么排除 `Library/`**：它是 Unity 自动生成的导入缓存，体积巨大（几个 GB）且可重建。提交它会让仓库爆炸，而且每次都有冲突。

**为什么 `ProjectSettings/` 必须提交**：它包含 Tag、Layer、物理矩阵、时间步长、Build 场景列表——**少了它，别人拉下来项目就跑不了**。你的 `TimeManager.asset` 就是这一类的关键文件。

**commit message 写法**：一行说清「做了什么」，正文说「为什么」。

```
feat(combat): 用对象池替换 HitSpark 的即时创建

每次命中都 new GameObject + AddComponent 会在连续命中时产生明显的
GC 抖动。改用 UnityEngine.Pool.ObjectPool 复用对象，并在 OnEnable
里统一重置状态。Profiler 实测战斗帧 GC Alloc 从 3.2KB 降到 0。
```

**作品集仓库的最低标准**：20 条以上有意义的 commit，而不是一次 `initial commit` 上传全部代码。**面试官会看 commit 历史来判断代码是不是你写的。**

## 8.2 asmdef 分层

**结论**：Assembly Definition 把代码切成独立编译单元，带来三个好处——编译更快、依赖被约束、测试可以独立运行。

**你项目里已经有正确的三层**

```
Assets/Scripts/ZMZZ.Runtime.asmdef            运行时逻辑
Assets/Editor/ZMZZ.Editor.asmdef              编辑器工具（可依赖 Runtime）
Assets/Tests/PlayMode/ZMZZ.Tests.PlayMode.asmdef   测试（可依赖 Runtime）
```

**依赖方向必须是单向的**

```
Tests  →  Runtime
Editor →  Runtime
Runtime ✗→ Editor     （运行时不能引用编辑器代码，否则打包失败）
```

**为什么编译更快**：改了 `Runtime` 之外的文件，不影响其他程序集的重新编译；没有 asmdef 时，任何一处改动都会让整个 `Assembly-CSharp` 重编译。

**为什么测试能独立运行**：测试程序集可以引用 `UnityEngine.TestRunner` 和 `NUnit`，而运行时程序集不该带这些依赖。

**面试延伸**：被问「为什么不用一个大程序集」，答「编译时间随代码量线性增长，分层之后改 UI 不会触发战斗模块的重编译；另外 asmdef 能强制依赖方向，防止运行时偷偷引用编辑器代码——这类错误往往到打包时才暴露。」

## 8.3 单元测试与 PlayMode 测试

**结论**：`[Test]` 测纯逻辑（EditMode），`[UnityTest]` 可以跨帧（PlayMode）。

| | EditMode | PlayMode |
| --- | --- | --- |
| 特性 | `[Test]` | `[UnityTest]` |
| 运行环境 | 不进入播放 | 进入播放，完整生命周期 |
| 能否跨帧 | 不能 | 能（`yield return null`） |
| 速度 | 快 | 慢 |
| 适合 | 纯函数、数值计算 | 组件交互、物理、场景行为 |

**你项目里的 12 个测试（这是简历亮点）**

```
Assets/Tests/PlayMode/CombatRulesTests.cs              战斗规则
Assets/Tests/PlayMode/UIFrameworkTests.cs              UI 框架
Assets/Tests/PlayMode/CombatPrototypeSceneTests.cs     场景行为
```

**为什么这对应届生是亮点**：绝大多数应届生的项目没有任何测试。主动写测试说明你理解「可验证性」——**而且这直接对应企业里「回归测试」的真实需求**。

**面试可以这么讲**：「我把伤害结算、格挡弹反这类纯规则抽成了可测试的逻辑，写了 PlayMode 测试覆盖它们。这样我改动 `DamageResolver` 之后能立刻知道有没有破坏既有行为——`CombatRulesTests` 就是我改数值时的安全网。」

## 8.4 代码规范与命名

**结论**：规范的目的不是好看，是让「同一件事只写一遍、同一类东西长一个样」。

**通用约定（你项目基本遵守了）**

| 项 | 约定 |
| --- | --- |
| 命名空间 | `ZMZZ.Combat`、`ZMZZ.UI`——按模块分，不按类型分 |
| 公开字段 / 属性 | `PascalCase`（`Health`、`Motor`、`Current`） |
| 私有字段 | `_camelCase`（`_stateFrame`、`_tuning`） |
| 局部变量 / 参数 | `camelCase` |
| 方法 | `PascalCase`、动词开头（`ApplyDamage`、`TryDodge`） |
| 常量 | `PascalCase` 或 `UPPER_SNAKE`，全项目统一 |
| 接口 | `I` 前缀（`IDamageGuard`） |

**「同一个规则只写一遍」的具体例子（你错题本里那条）**：文件名、路径、key 名只要在两处各写一遍，迟早会不一致。你项目里的正面案例是 `SceneNames.cs`——把场景名集中成一个类，而不是在各个文件里写字符串。

**自检清单第 1 条的反面案例**（`_x == null` 写反成 `_x != null`）：这类错误不报错、只静默失效。**规范里最值钱的一条是「每个查表函数失败时都要打日志」**——因为这直接决定你能不能快速定位 bug。

# 附：背不下来的时候，记住这 10 句

1. 值类型装数据，引用类型装地址；值类型存在**它被声明的位置**。
2. 看到「值类型赋给 `object` 或接口」，就有装箱。
3. `MonoBehaviour` 占掉唯一的继承名额，所以「能力」用接口。
4. `TryGetValue` 查一次，`ContainsKey` + 索引器查两次。
5. Unity 的 GC 是 Boehm，**不是分代**。
6. 帧计数是确定性的，`deltaTime` 累加会漂移。
7. `Time.deltaTime` 受 `timeScale` 影响，`unscaledDeltaTime` 不受。
8. 对象池里被复用的对象**不会**再走 `Awake`，重置逻辑放 `OnEnable`。
9. `Resources` 全量打进包、无法精确卸载——正式项目用 Addressables。
10. 优化不是「做了几件事」，是「测量 → 定位 → 修改 → 复测」的闭环。
