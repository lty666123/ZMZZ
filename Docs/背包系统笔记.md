## 0. 整体设计：四层结构

背包系统由四层组成，**每层只管一件事**。这是整份笔记最重要的部分。

| 层 | 是什么 | 形式 | 例子 |
| --- | --- | --- | --- |
| ① 配置 | 物品的"说明书" | **ScriptableObject 资产** | 红药水：id=potion_hp，最多叠 99，喝了回 50 血 |
| ② 状态 | 你**现在**有什么 | 纯数据类（**要存档**） | 背包第 0 格：potion_hp × 5 |
| ③ 逻辑 | 增删查改的规则 | 普通 C# 类 | 加物品时先堆叠、再找空格 |
| ④ 表现 | 把状态画出来 | UI 面板 | 格子显示图标和数字，点击使用 |

### 为什么必须分四层（三个具体好处）

1. **改数值不用改代码** —— 药水回血量 50 改 80，只改资产，代码不动
2. **存档变简单** —— 只存"id + 数量"（②层），不存整个说明书
3. **界面可以随便重做** —— ④层只是"把②层画出来"，③层逻辑完全不动

> **最容易犯的错**：把这几件事混在一个 UI 脚本里写。结果加个物品要改界面代码，存档还得遍历 UI。

### 附加的两条硬规则

**规则一：配置和状态绝不能混**

- `ItemDefinition` 是"说明书"——所有红药水共用一张
- `ItemStack` 是"你现在手上的"——每个存档各不相同

混了的后果：捡了一瓶药水，全世界的药水都变成 2 瓶。

**规则二：状态里只存 id 和数量，绝不存资产引用**

因为**存档只能存文本**，存不了"指向某个资产文件的指针"。写 `public ItemDefinition item;` 存进 JSON 会变成一串无意义数字，读回来是 null。

商业项目的铁律：**存档只存 id（字符串）+ 数量**，读取时用 id 去查表拿说明书。

## 1. 已完成（第 1 步）：物品说明书

**文件**：`Assets\Scripts\Inventory\ItemDefinition.cs`

```csharp
using UnityEngine;

public enum ItemType { Consumable, Material, Weapon, Armor }

[CreateAssetMenu(fileName = "Item_", menuName = "ZMZZ/物品定义")]
public class ItemDefinition : ScriptableObject
{
    public string id;              // 唯一编号，存档靠它认人
    public string displayName;     // 玩家看到的名字
    public Sprite icon;
    public ItemType type = ItemType.Material;
    public int maxStack = 99;      // 一格最多叠几个；装备填 1
}
```

### 关键点

**为什么用 ScriptableObject（而不是普通脚本 + 字典）**

| | 平时写的脚本 | ScriptableObject |
| --- | --- | --- |
| 是什么 | 挂在物体上的**行为** | 一个能存数据的**资产文件** |
| 谁用 | 程序员 | **策划**（在 Inspector 里填数字） |
| 改数值要重编译吗 | 要 | **不用** |

**`[CreateAssetMenu]` 的作用**：加上它，Project 窗口右键就能创建这种文件（菜单里出现 `ZMZZ/物品定义`）。

**为什么用 `id` 而不是用名字当标识**：名字会被改（"红药水"→"治疗药水"），`id` 定下来就永不改，**存档存的是 id**。

### 约定

- 物品资产统一放在 **`Assets\Resources\Items\`**（路径不能改，代码按这个路径找）
- `id` 命名建议：小写下划线，例如 `potion_hp`、`sword_01`

## 2. 已完成（第 2 步）：背包状态数据

**文件**：`Assets\Scripts\Inventory\ItemStack.cs`

```csharp
[System.Serializable]
public class ItemStack
{
    public string itemId = "";   // 指向 ItemDefinition 的 id；空字符串 = 这一格是空的
    public int count;

    public bool IsEmpty { get { return string.IsNullOrEmpty(itemId) || count <= 0; } }
}
```

**文件**：`Assets\Scripts\Inventory\InventoryData.cs`

```csharp
using System.Collections.Generic;

[System.Serializable]
public class InventoryData
{
    public int version = 1;                                // 存档版本号
    public int slotCount = 20;                             // 一共几格
    public List<ItemStack> slots = new List<ItemStack>();   // 格子的内容
}
```

### 关键点

**`[System.Serializable]` 必须有** —— 加上它，Unity 和 `JsonUtility` 才肯保存这个类。**漏掉不会报错，只会静默存成空 `{}`**（错题本第 4 条）。

**空格用空字符串，不用 null** —— `null` 存进 JSON 容易出问题，空字符串最安全。

**`IsEmpty` 写成属性（不是字段）** —— 属性不会被存进存档，所以"算出来的值"都写成属性。

**为什么 `slots` 永远是固定 20 个元素**（空格也占位）：

1. **JsonUtility 保存带 null 元素的列表会出问题**
2. 界面画格子时，"第 i 格"必须永远对应 `slots[i]`

**`version` 现在没用，但一定要留** —— 以后改结构（比如加耐久度）时靠它判断老存档能不能读。

### 注意

`slotCount` 一旦存进存档，**之后改默认值对老存档无效**（老存档里的 20 会覆盖代码里的 30）。

## 3. 知识点：人话 → 代码

### 查表的固定句型（`TryGetValue` + `out`）

```csharp
if (map.TryGetValue(id, out def)) return def;
```

人话：「在 `map` 里用 `id` 查；**查到了**就把 `def` 返回；查不到往下走。」

| 写法 | 找不到时 |
| --- | --- |
| `map[id]` | **抛异常**，程序崩 |
| `map.TryGetValue(id, out def)` | **返回 false**，不崩 |

`out` 的含义：普通参数是"我把值传进去"，`out` 是"**你把值放进来给我**"。所以必须先声明变量：

```csharp
ItemDefinition def;                     // 先准备一个空盒子
if (map.TryGetValue(id, out def))       // 查到了，盒子就被填上
{
    return def;
}
```

**通用模板**（以后遇到查表就套）：

```csharp
结果类型 结果变量;
if (字典.TryGetValue(要找的key, out 结果变量))
{
    // 查到了，结果变量里就是东西
}
else
{
    Debug.LogWarning("没查到：" + 要找的key);   // 查表失败一定要留痕
}
```

### 静态类的"懒加载"（看起来像自动调用）

```csharp
public static class ItemDatabase
{
    static Dictionary<string, ItemDefinition> map;

    static void EnsureLoaded()          // ← 它不会自动被调用
    {
        if (map != null) return;        // 加载过就直接走人（缓存标记）
        map = new Dictionary<string, ItemDefinition>();
        foreach (var def in Resources.LoadAll<ItemDefinition>("Items")) ...
    }

    public static ItemDefinition Get(string id)
    {
        EnsureLoaded();                 // ← 是我手写的这一行在调它
        ...
    }
}
```

**原理**：每次 `Get()` 进来都顺手做一次"要不要加载"的检查 —— 第一次真加载，之后只花一次 null 判断。

**为什么这么设计**：`Resources.LoadAll` 要读硬盘，很慢。全在启动时加载会让启动卡几秒；每次都加载又太慢。懒加载折中：**第一次用到才读，读完记住**。

**怎么分辨"自动调用"**：

| 方法 | 谁调它 |
| --- | --- |
| `Awake` / `Start` / `Update` / `OnCollisionEnter2D` | Unity 用反射**自动**调 |
| 其他任何名字 | 一定有人在某处**手写**了它（搜名字就能找到） |

**一个坑**：`static` 字段在整个运行期间只有一份。如果项目关掉了 Domain Reload，**重进播放时会带着上一局的脏数据**。商业做法是加一句：

```csharp
[RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.SubsystemRegistration)]
static void ResetStatic() { map = null; }   // 每次进 Play 前清一遍
```

### 第 4 步的设计要点（先记着）

`Inventory.Add(itemId, count)` 的逻辑顺序：

1. 先往**已有的同类格子**里堆（受 `maxStack` 限制）
2. 还没放下，再**找空格**放
3. 都放不下 → **返回剩下没放下的数量**

**为什么返回"没放下的数量"而不是 true/false**：调用方需要知道"掉了几个"，才能决定是弹提示、还是让物品掉在地上。
